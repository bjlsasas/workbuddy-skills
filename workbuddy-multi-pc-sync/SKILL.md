# WorkBuddy 多电脑实时同步

WorkBuddy 是**配置在本机的 Agent**——技能、专家、配置只存在当前这一台电脑上，换一台就用不上。
本技能把它们同步到**你名下的每一台电脑**（公司机 / 笔记本 / 家里那台），并让**专家在每台机器上真的能用**：像 OneDrive 同步文件一样，同步你的 WorkBuddy。

**这个技能给谁用**

- 你有不止一台电脑（公司的、笔记本、家里的），每台都装了 WorkBuddy
- 你在其中一台上配好了技能、专家、工作区，希望换到任何一台都能直接用
- 你已经能把文件夹同步出去，却发现「文件到了，专家没用」——问题出在登记层

# 上篇 · 认知与判读（不装脚本也看得懂）

## 一、原理：先分清两层，否则永远修不好

### 第 1 层 · 文件层（Syncthing，双向，自动）

四夹，全部 `sendreceive`（双向）。**任何一侧增改删，另一侧跟着变。**

| 夹名 | 指向 | 内容 |
|---|---|---|
| `wb-skills` | `~/.workbuddy/skills` | 全部技能 |
| `wb-experts-market` | `~/.workbuddy/plugins/marketplaces/my-experts` | 专家**源包** |
| `wb-experts-cache` | `~/.workbuddy/plugins/cache/my-experts` | 专家**运行副本**（真正被加载的） |
| `my-workspace` | 工作区目录 | 全部成果、脚本、记忆 |

### 第 2 层 · 登记层（本机，不自动）

专家要在界面里出现，还差三处本机登记 —— **它们不在同步夹里，也绝不能跨机复制**：

| # | 位置 | 为什么不能拷 |
|---|---|---|
| ③ | `plugins/installed_plugins.json` | `installPath` 是**含用户名的绝对路径** |
| ④ | `plugins/known_marketplaces.json` | 同上 |
| ⑤ | `settings.json` → `enabledPlugins[...]` | 本机开关 |

**这两层的分工是全部问题的根源，也是全部答案：**

> 文件同步不覆盖登记层。**哪台机器收到了变动，就在哪台机器补一次登记。**
> 不补的后果不是报错，而是**静默继续跑旧版本**，界面看不出任何异常。

**推论（很多人会搞错）：**
- 技能靠**扫目录**认，不进 ③④⑤ → 文件到了，重启 WorkBuddy 就有。
- 专家靠 ③④⑤ → 文件到了**不等于**生效，必须跑自愈。
- **双向都能改**：笔记本上新增/调优专家，文件会回传主力机，但**主力机要补登记**。
  不存在"只能在某一台上改"这回事。

上面讲的是原理，这一节讲**用户会怎么用它** —— 也就是你在对话里说一句什么样的话，就会把这个技能唤起来。

### 四类典型请求（按发生频率排序）

| # | 用户说什么（原话） | 技能做什么 | 产出形态 |
|---|---|---|---|
| 1 | 「我要把两台电脑（笔记本 + 台式）的 WorkBuddy 同步起来」「怎么让另一台也能用我的专家和技能」 | 输出四夹配置 + 双向配对 + 五层登记清单（逐步可勾选） | step-by-step 操作清单 |

| 3 | 「连上 2 秒就断、无限循环、一个字节都过不去」 | 9 字符 `encryptionPassword` 真凶定位（本技能最硬的一条） | 定位 + 修复 + 复验三步 |
| 4 | 「我感觉没在同步」「到底在不在同步？怎么确认成功？」 | 四处取证（进程 / 端口 / 四夹状态 / 日志按天统计），用数据回答 | 取证报告 |

| 用户可能会说 | 实际不属于本技能 |
|---|---|
| 「把我的技能发布到 WorkBuddy 开放平台」 | 那是**对外发布**，与本地多机同步是两回事 |
| 「同步我的文件夹 / 照片 / 下载」 | 本技能只管 **WorkBuddy 四个目录**（技能/专家源包/专家副本/工作区） |
| 「把数据同步到云端 / 手机」 | 本技能是 **PC 到 PC**；云端另有机制 |
| 「帮我把这台电脑重装后一键复原」 | 可以做，但属于由此派生的迁移任务，需单独规划 |

## 二、标准作业流程（每接入一台新机器）

### 1. 装同步客户端

**先分清一件事**：Syncthing **不是本技能自带的东西** —— 它是**第三方开源软件**（约 27 MB 的可执行文件），装在**操作系统**里、跑在 WorkBuddy 之外。技能包只有一百多 KB，**不可能把软件本体打进来**，所以**每接入一台新电脑，都要在那台机器上装一次**（装过的机器不用重复装）。

**但「要装一次」不等于「要你自己去研究怎么装」。** 两条路任选：

| 走法 | 怎么做 |
|---|---|
| **① 让 AI 代劳（推荐）** | 直接说「帮我在这台机器上装 Syncthing」。技能会带 AI 走完：探测是否已装 → 下载官方 zip → 校验 → 解压到固定目录 → 打印 `syncthing.exe` 真实路径。你只在需要提权时点一下「允许」 |
| **② 包内脚本自己跑** | `python scripts\装Syncthing.py --check`（只探测，不下载）→ 去掉 `--check` 即下载安装。用 `--dir <目录>` 指定安装位置 |

**手动下的话**（AI 代劳走的也是下面这两个渠道）：

| 渠道 | 地址 | 说明 |
|---|---|---|
| **官网下载页（首选）** | `https://syncthing.net/downloads/` | 找 **Base Syncthing** 那一栏的 **Windows → Intel/AMD (64-bit)**，下到的是 zip |
| GitHub Releases（备用） | `https://github.com/syncthing/syncthing/releases/latest` | 文件名形如 `syncthing-windows-amd64-v<版本>.zip`。官网打不开时走这条 |

**选哪个**：下 **Windows 64 位便携版（zip）**。不要用第三方的「Windows Setup」安装器版 —— 便携版解压即用、不写注册表、不装服务，符合本技能「放工作区之外、自己掌控」的前提。（版本号会随时间变，看文件名里 **amd64** 就对了。）

**放哪**：解压后整个目录放**工作区之外**（否则会自我同步）。给每台机器固定版本目录，例如 `<同步工具目录>\syncthing\`。

**★ 两台机器不必是同一版本**，但**夹定义（下一节的 `id`）必须逐字一致**。版本混用在 Syncthing 上是允许的。

### 2. 建四夹

用 REST API（`/rest/config/folders`）建，每个夹指定 `id` / `label` / `path`，并把设备加进 `devices`。
**文件夹 `id` 两台必须逐字一致**，否则不会互认。

**可直接照抄的四夹骨架**（把 `<用户名>` 与 `<对端设备ID>` 换成实际的，
`~/.workbuddy` 在 Windows 上即 `C:\Users\<用户名>\.workbuddy`）：

```json
[
  {"id": "wb-skills",         "label": "WorkBuddy 技能",
   "path": "C:\\Users\\<用户名>\\.workbuddy\\skills",
   "type": "sendreceive", "devices": [{"deviceID": "<对端设备ID>"}]},
  {"id": "wb-experts-market", "label": "WorkBuddy 专家源包",
   "path": "C:\\Users\\<用户名>\\.workbuddy\\plugins\\marketplaces\\my-experts",
   "type": "sendreceive", "devices": [{"deviceID": "<对端设备ID>"}]},
  {"id": "wb-experts-cache",  "label": "WorkBuddy 专家运行副本",
   "path": "C:\\Users\\<用户名>\\.workbuddy\\plugins\\cache\\my-experts",
   "type": "sendreceive", "devices": [{"deviceID": "<对端设备ID>"}]},
  {"id": "my-workspace",      "label": "工作区",
   "path": "<工作区绝对路径>",
   "type": "sendreceive", "devices": [{"deviceID": "<对端设备ID>"}]}
]
```

**要点**：
- `id` 是**身份**，两台必须**逐字节一致**（`wb-skills` 就是 `wb-skills`）；`label` 随便起，只给人看。
- `type` 保持 `sendreceive`（双向）。
- **`encryptionPassword` 一个字都不要写**（连空串也别主动加到这里；见 §四 第一条 —— 这是"连上 2 秒就断"的头号真凶）。
- 市场名默认 `my-experts`；若你的专家来自别的市场，把 `my-experts` 换成对应市场名（`plugins\marketplaces\<市场名>` 与 `plugins\cache\<市场名>` 两处要一致）。

### 3. 双向配对

Syncthing 必须**双方互相添加**才能连。只加一边 = 永远 `connected=false`。
取对端 ID：面板「操作 → 显示 ID」，或 `/rest/system/status`。

**★ 配对前先核对对端 ID 是不是"真身"。** 同一台机器可能因换 `--home` 目录而生成过多个身份；
拿旧 ID 去找人永远找不到，且现象是"看起来配好了但连不上"。

### 4. 落登记（关键一步）

在对端跑 `heal-expert.py`（见下节）。跑完**完全退出 WorkBuddy 再打开**。

### 5. 装开机自启（两件事，别混）

| 目标 | 做法 |
|---|---|
| 同步进程自启 | 启动文件夹放**纯 ASCII** 启动器（`schtasks` 常被安全策略拉黑，COM 也可能被禁） |
| 专家登记自愈 | 注册表 `HKCU\...\Run` 写一条，指向 `pythonw.exe "<脚本>"` |

## 三、自愈脚本（可选加速器）

> **先读这段再决定要不要装。**
>
> 上篇的认知与对照表**不需要任何脚本**：知道两层分工、会按症状对号、会用 §十七 的口径取证，
> 绝大多数问题就能自己定位。脚本解决的是"**不想每次手工查**"——把巡检、体检、自启、
> 忽略规则登记这些固定动作自动化。
>
> **Python 不用你操心 —— WorkBuddy 自带运行时。** 包内每个启动器（`.bat`）按固定顺序找解释器：
> ① `%USERPROFILE%\.workbuddy\binaries\python\versions\<版本>\python.exe`（**WorkBuddy 自带；装了 WorkBuddy 就有**）
> → ② 该目录下的任意版本 → ③ 系统 `py -3` → ④ 系统 `python`。
> **结论：只要这台机器上装着 WorkBuddy，脚本就能跑，你不需要另外去装 Python。**
> 唯一例外：要在**没装 WorkBuddy 的机器**上单独跑这些脚本（罕见）—— 那就到
> `https://www.python.org/downloads/windows/` 下 Python 3（3.9 以上），装时**勾上「Add python.exe to PATH」**，
> 敲 `python --version` 能看到版本号即就绪。**装 Python 不影响 WorkBuddy**，也不会被本技能改动。
> 脚本**不含任何个人路径与设备 ID**，首次运行会自动探测 Syncthing 位置与双方身份；若布局特殊，把包内的
> `sync-heal-config.example.json` 复制为 `sync-heal-config.json` 再改即可（见下方“配置模板”）。

发布包 `scripts/` 下，共 12 个可跑文件（全部纯 ASCII 名）+ 1 份配置模板：

| 文件 | 作用 |
|---|---|
| `装Syncthing.py` | **装环境（第 0 步）**。探测本机是否已有 Syncthing → 没有则从官方渠道取最新 Windows 64 位便携版 → SHA256 校验 → 解压到固定目录 → 打印 `syncthing.exe` 真实路径。`--check` 只探测不下载；`--dir <目录>` 指定位置 |
| `shconfig.py` | **配置层**。公开 API：`workspace()` / `coop_dir()` / `relay_dir()` / `dist_dir()` / `folder_ids()` / `peer_id()`… 优先级：配置文件 → `SYNCHEAL_*` 环境变量 → 内置默认 |
| `shdetect.py` | **运行时自动探测**。**零机器常量**：进程枚举（Win32 API）、端口、`config.xml` 定位、API key、`myID`/`peerID`、真实桌面 |
| `heal-expert.py` | **核**。扫源包 → 读版本 → 补/校验 cache 运行副本 → 修 ③④⑤ |
| `guard.py` | 加密口令与设备登记护栏（每轮先跑） |

## 五、红线（违反会损坏数据）

1. **`workbuddy.db` 永不入同步夹。** 带 WAL 的活跃 SQLite，自动化/会话/空间三类界面数据都在里面；
   两台同写会冲突甚至损坏库。跨机只能走「本机脚本生成」「本机打开一次」的正当路径。
2. **`storage/.../scoped/<hash>/` 每机不同，拷目录无效。**
3. **不动别人的个人目录。** 清理前必须逐项列出 → 用户确认 → 走回收站，不用 `rm -Force`。
4. **`versioning` 里 `type` 才是策略**（如 `staggered`），**`fsType` 只能是 `basic`/`fake`**。
   把 `type` 的值顺手填给 `fsType` → 冲突归档全线失败（会静默卡住一批文件，含 `marketplace.json`）。
5. **写死的 IP 是易碎品。** 重连 WiFi / 路由重启就可能变；对端 `addresses` 必须**同时保留 `dynamic`**。
   报 IP 前一律现场取，别读记忆里的旧值。
6. **绝不用 REST `/rest/system/restart` 去重启同步进程。** 本机实例一律以 `--no-restart` 启动，
   该接口会让进程**直接退出且不复活**，同步彻底停摆（2026-09-19 真实踩到，用户侧表现为「突然全都不动了」）。
   要重启就：杀进程 → 双击启动器。
7. **调本机 REST API 必须绕过系统 HTTP 代理。** 环境里存在 `http_proxy`（如 `http://127.0.0.1:6592`）时，
   请求 `127.0.0.1:8384` 会被转发出去并返回 **502 Bad Gateway** —— 看起来像服务崩了，其实服务好好的。
   Python：`urllib.request.build_opener(urllib.request.ProxyHandler({}))`；curl：`--noproxy '*'`。
8. **配置里凡有中文，绝不用 PowerShell 写。** PS 5.1 的 `Set-Content` / `Out-File` / `Invoke-RestMethod`
   在没显式指定 UTF-8 时按系统 ANSI 码页处理字符串 —— 中文进去、mojibake 出来，而**冲突目录永不报错**，
   只会静默指着一条不存在的路径。落盘/落库带中文的配置一律走 **Python + `encoding='utf-8'`**；
   给对端的脚本**源文件保持纯 ASCII**，中文写 `\uXXXX` 转义（见第九节）。
9. **给对端的修复指令，先热修、后重启。** REST 改配置是**热生效**且不动进程；只有 REST 完全不可用时
   才走「杀进程 → 改文件 → 重启单实例」。**别默认让用户重启** —— 多一次重启就多一次「守护进程起不来」的风险。

## 六、踩坑速查（都是真金白银换来的）

| 坑 | 现象 | 正解 |
|---|---|---|
| `\b` 转义 | 生成脚本时 `\.workbuddy\binaries` 变成 `.workbuddyinaries` | 用 Write 工具写生成脚本 + raw 字符串，**绝不走命令行/heredoc 传反斜杠** |
| cmd 中文劈行 | `.bat` 某分支莫名失败 | **bat 正文一律纯 ASCII**；中文名脚本由 ASCII 名启动器（`runpy`）去叫 |
| 启动器自引用 | `%~dp0` 在启动文件夹里指向自己 | 烤入绝对路径 |
| `$home` 只读 | PowerShell 里赋值被静默忽略，参数变成 `C:\Users\<用户名>` | 换变量名 |
| pythonw 无 stdout | 后台运行直接抛异常 | 开头 `if sys.stdout is None: sys.stdout=open(os.devnull,'w')` |
| `.stignore` 写不进 | `PermissionError`（Syncthing 占句柄） | 写临时文件 + `os.replace` **原子替换** |
| 沙箱回收子进程 | 命令跑完进程就没了 | 用户双击 或 注册表 Run 键 |
| `schtasks`/COM 被拉黑 | 计划任务建不了 | 走 `HKCU\...\Run`（免管理员）或启动文件夹 |
| shell shim 间歇失效 | `rm`/`ls`/`tail`/`dirname` 报 not found | 文件增删查一律走 Python |
| HTTP 代理劫持本地 API | 本机 `127.0.0.1:8384` 回 502，误判成服务崩溃 | 绕过代理（红线 7） |
| REST restart 自杀 | 调完重启，进程再也不出现 | `--no-restart` 实例的通病；杀进程 + 双击启动器（红线 6） |
| 直传服务起不来 | Bash 起的 8000 服务跑完即被回收；`Start-Process`/`Invoke-CimMethod Win32_Process.Create` 均被安全策略禁 | 落到桌面**纯 ASCII** `.bat`，由用户双击 |
| `/rest/system/disconnect` 在 2.1.5 上没了 | 调用返回 `404 Not Found`（老教程里的接口） | 改用 `POST /rest/system/pause?device=<id>` → 等几秒 → `POST /rest/system/resume?device=<id>`，效果是**强制重建会话并重新交换集群配置与索引** |
| `$home` 之外，`$hd` 也可能踩 | 给对端写指令时把配置目录塞进自动变量名 | 一律用 `$hd` / `$cfg` 这类非保留名，并在指令里**明写提醒** |
| 两个 `syncthing.exe` 被误判成「双实例」 | 命令行一个带引号、一个不带，看着像两套 | **先看 `ParentProcessId`**：两条互为父子、创建时间相差不到 1 秒 = Syncthing 正常的主/工作双进程结构（父进程命令行来自 `.bat` 的 `start "" "…exe"` 故带引号，子进程由 Go 的 `os/exec` 重建故不带），**不是故障，不要杀**。只有两个 PPID 互不相干且都指向 `explorer`/`cmd` 才是真双实例 |
| **`syncthing.log` 的时间戳是空格分隔** | 用 `l[:19] >= '2026-09-19T15:00:00'`（ISO 的 `T`）筛日志，**一条都选不出来**，误判成「这段时间没有错误」 | 日志行形如 `2026-09-19 15:12:36 ...`，**第 11 个字符是空格不是 `T`**（空格 0x20 < 'T' 0x54，所以全部比较失败）。比较串必须同格式：`datetime.now().strftime('%Y-%m-%d %H:%M:%S')`。写日志分析脚本时先 `print(repr(lines[0][:20]))` 确认格式 |
| **★ 用 REST PUT 改配置时「省略字段」不等于清空** | 以为没写就等于恢复默认，实际 **Syncthing 会保留旧值** —— 表现为「改完读回来还是旧的、故障修了但没变」，最耗时间（v11 就是这么空转了一轮） | **要清空就显式写出空值**：`"encryptionPassword": ""`、`"paused": false`、`"untrusted": false`、`"fsType": "basic"`。改完**必须读回来复核**，别信 `HTTP 200` |
| **★ 报了错却看不见错** | 断连的报错生成在**对端**（接收方），本机日志干净 → 误判成"注入无效/配置没问题" | 判断因果别只看日志，**看连接状态**（`/rest/system/connections` 的 `connected`）与字节计数；要做受控实验（见 11.3） |
| PowerShell 写中文 → mojibake | 用 `Set-Content`/`Out-File`/`Invoke-RestMethod` 写含中文的配置或 JSON 体，落盘/落库变乱码 | PS 5.1 默认按系统 ANSI 码页处理字符串。**配置里凡有中文一律改用 Python**；JSON body 用 `json.dumps(..., ensure_ascii=True).encode('ascii')`，让字节流里根本不存在非 ASCII |
| 把自己机器上的测试脚本当无害的 | 写「重定向 CFG 到副本」这种测试桩时，若替换串含 Windows 路径，`re.sub` 会把 `\U` 当转义解析甚至写错文件 | 用 `lambda` 作 `repl` 避免转义处理；并在执行前 `assert` 目标路径位于临时目录（双保险） |
| **REST 改 folder 时漏掉 `devices` 字段** | 把该夹的共享列表整条覆盖成空、或只剩自己 → 对端连上即断，死循环（即第四节第一条的成因） | `PUT /rest/config/folders/<id>` 必须提交**从 GET 拿到的完整对象**，并**显式重写** `devices = [{deviceID:自己},{deviceID:对端}]`；提交后立刻 GET 回读核对 |
| **只查本机配置就下结论** | 本机四个夹都含对端 → 误判成「共享没问题，去查磁盘」 | 共享关系是**双向各存一份**。要判定链路成立必须**两边都查**：本机看 `devices` 含不含对端，对端看 `devices` 含不含本机。够不着对端时，只能靠本机日志里的 `cluster-config` 报错间接定性 |
| **★ 子进程中文输出经管道捕获变乱码** | 加固包报告里 `[4]` 段是 `ͬ������`，而 `[5]` 段正常 —— 同一份报告一半乱一半不乱 | 子脚本 stdout 被重定向时**退化成系统 ANSI（GBK）**，父进程按 UTF-8 解码即乱。**两侧都要做**：子脚本开头 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`，父进程 `subprocess.run(..., encoding="utf-8")`。诊断口诀：**同一批输出里「有的乱有的不乱」，差的一定是那两个脚本自身有没有 reconfigure** |
| **★ 真实桌面不在 `C:\Users\<用户名>\Desktop`** | 报告"桌面已清空"，用户桌面上东西一个没少（那个是空壳） | 桌面/文档/下载的真实路径由 `HKCU\...\Explorer\User Shell Folders` 决定 —— 本机四项**全部被改到了非系统盘**（盘符与目录名都可能与默认完全不同）。**动用户目录前一律先查注册表读真值**，别拿惯用路径去猜 |
| **★ `installed_plugins.json` 里单条记录可能是 `dict` 不是 `list`** | `heal-expert.py` 读清单时 `KeyError: 0` 直接崩，**等于「开机自愈」一直跑不完整**却没人发现 | 72 条里 71 条是 `list`，被应用重写过的那条是 `dict`（`{"scope":…,"installPath":…}`）。**读的时候两种都认、写回时保持原形态**（改约定会与对方来回改写）。判定"谁写的"有个巧办法：比 `lastUpdated` 格式 —— 本脚本 `utcnow_iso()` 产出 `...T16:45:15.000Z`，应用写的是 `...T16:45:15`（无毫秒无 Z） |
| **★ 有两份 `syncthing.log`，根目录那份是过期残留** | `<同步工具目录>\syncthing\syncthing.log`（3 KB，停在 09-19）看着像"日志没新内容"；真日志其实是 `data\syncthing.log`（1.6 MB，当天还在写）。**照旧路径读 → 误判成「三天没同步」** | 读日志前先比两份的 `getmtime/size`，取**新的那份**。便携版 Syncthing 的活日志在 `--home` 指向的目录里（即 `data\`）；根目录那份是老版本或早期启动留下的 |
| **★ 沙箱内派生的 `syncthing.exe` 照样被回收（比踩坑表第 9 条更细）** | 用 `Popen` + `DETACHED_PROCESS\|CREATE_NEW_PROCESS_GROUP` 拉起，**当场成功**：2 秒内 8384 就绪、REST 能读、状态正常。但**下一次工具调用时进程已消失** | "当场能跑"≠"活得下来"。判断存活要在**下一次工具调用**里再枚举一次进程。要它常驻只有一个正解：**用户双击启动器** 或 登录自启。别用"我起了、端口通了"当结论 |
| **★ REST 返回 `403 Forbidden` 而不是拒连 —— 是 API Key 缺失，不是服务没起** | 与"端口没开"（`connect_ex != 0`）混淆，误判成"服务崩了"反复重启 | `connect_ex == 0` 但请求 403 = 端口活着、缺凭据。**取 key 正解**：读 `config.xml` 的 `<apikey>`，请求带 `X-API-Key` 头。注意老教程里 `/rest/system/status` 不带 key 也能读，新版会拦 |

## 八、管道卡住时的绕行直传（不要死等同步）

当接收方迟迟不来取、又暂时够不到那台机器时，**别耗着** —— 走局域网 HTTP 直传，分钟级解决。

**主力机侧准备**

1. 把要过去的文件打成一个**小包**（几十 KB 即可，别把整包都塞进去），放到固定目录，例如 `<同步工具目录>\share\`。
2. 写一个 `index.html` 下载页放进同目录；**页面里明写当前 IP**（每次现场取，别用旧值）。
3. 起服务：`python -m http.server 8000 --bind 0.0.0.0 --directory <该目录>`
4. **加防火墙入站规则**（不加则对端连不上）：
   `netsh advfirewall firewall add rule name="ZGH-Sync-Share-8000" dir=in action=allow protocol=TCP localport=8000 profile=any`
5. 桌面放一个**纯 ASCII** 启动器 `.bat`（先 `ipconfig | findstr IPv4` 打印当前 IP，再起服务，最后 `pause`），
   **由用户双击** —— 本机自己起的服务会被沙箱回收，`Start-Process` 与 WMI 创建进程也被安全策略禁止。

**对端侧**

6. 浏览器打开 `http://<主力机IP>:8000` → 下载小包 → 解压 → 放进与主力机同名的目录 → 继续后面的流程。

**纪律**：直传是**绕行**，不是替代。管道的问题仍要在对端查清并修好（第四节），
否则下一次新增文件还会卡在同一个地方。

## 九、给对端写修复指令的铁律（血泪版）

跨机排障时，**指令本身就是风险源** —— 2026-09-19 的 path 乱码事故，成因就是一条不够硬的指令。

### 1. 代码块必须逐字节纯 ASCII

中文只出现在 markdown 正文；**所有 Python 代码块里不得出现任何 >0x7F 的字节，连注释也不行**。
路径里的中文目录名（如 `笔记本部署包`）要拆成转义拼接：

```python
CFG = <YOUR_SYNC_HOME> + r'\syncthing\data\config.xml'
```

这样无论对端用什么编码保存、复制粘贴经过什么环节，脚本都不可能被写坏。

交付前自检（从 md 抽出代码块逐个查）：

```python
import io, re
md = io.open('instruction.md', encoding='utf-8').read()
for i, b in enumerate(re.findall(r'```python\n(.*?)```', md, re.S), 1):
    bad = [c for c in b if ord(c) > 127]
    print('block%d non-ascii=%d' % (i, len(bad)))
```

### 2. 优先热修，别让用户重启

`PUT /rest/config/folders/<id>` 改 path/label 是**热生效**：进程不动、连接不掉、立刻重扫。
只有 REST 完全不可用才退到「杀进程 → 改 `config.xml` → 重启单实例」。
**任何情况下都不要让对端点 GUI 的「重启」**（红线 6）。

### 3. 中文路径的修复配方（REST 版，首选）

```python
f = api('/rest/config/folders/my-workspace')
f['path']  = <YOUR_WORKSPACE_UNICODE_ESCAPED>
f['label'] = '\u5de5\u4f5c\u533a-' + '\u8bf8\u845b\u5c0f\u82b1'
api('/rest/config/folders/my-workspace', 'PUT', f)
```

要点：`json.dumps(..., ensure_ascii=True).encode('ascii')` + `Content-Type: application/json; charset=utf-8`
+ **绕开系统代理**（红线 7）。改完回读 `config.xml` 里那一段 folder 开标签确认落盘正确。

### 4. 改之前先确认目标目录真实存在

`os.path.isdir(NEWP)` 必须先为真，否则改完仍是「指到不存在的路径」。
全盘找真实目录同样用纯 ASCII 脚本，按**码点转义**匹配：

```python
NAME = <WORKSPACE_NAME_UNICODE_ESCAPED>
MARKS = (NAME, <MOJIBAKE_PREFIX_1>, <MOJIBAKE_PREFIX_2>)   # real name + mojibake fragments
```

### 5. 指令交付前跑一次隔离自测

抽出指令里的代码块：**逐块 `py_compile` 验语法 + 验纯 ASCII**；涉及改配置的段落，
用**真实配置的副本**（放临时目录，并 `assert` 目标不在真实路径）实跑一遍，断言
「改前是坏的 → 改后是对的、其余字段一字未动、XML 仍可解析、二次执行幂等」。

参考实现：指令交付前的**隔离自测套路** —— 发布包 `tests/` 下各套即为同一做法的成品（合计 57/57）。

### 6. 优先交付「一键脚本」，别交付「要用户手敲的代码块」

教训（09-19）：v7 / v8 / v9 三轮都是把 4–5 段代码块交给用户，让他在对端的
PowerShell 里逐段粘贴执行。结果**连续三轮跑不通**——用户要么漏段、要么选错窗口、
要么执行到一半被别的事打断；而 Agent 拿不到任何中间输出，只能再猜一轮。
更糟的是，用户手敲 `Set-Content`/`Invoke-RestMethod` 写中文，本身就是 mojibake 事故的来源。

**改法（定为标准姿势）**：

- 把「预检 + 修复 + 复验」**全部塞进一个脚本**：`一键修复xxx.bat`（正文纯 ASCII）
  + `xxx.py`（UTF-8 源），连同一份指令 md 打成一个 zip
- 用户只做两件事：**拿到 → 双击**。脚本自己打印全过程，跑完 `pause` 停住，用户整段回报
- 脚本必须自带三件套：**动手前备份**（`config.xml.bak-时间戳`）、**`--check` 只读模式**、
  **结尾复验并给出人话结论**（「已连通，开始拉数据」/「仍未连通，把窗口发回」）
- 脚本内定位自己（exe / `--home` / `myID`）**一律运行时探测**，不写死机器路径

### 7. 交付位置必须「明确到能双击」（补）

**只给一个 URL ≠ 交付。** 用户反馈原话：「不要再让我通过笔记本打开链接下载东西了，
根本没有下载的按钮，我也不知道文件在哪里」。所以：

- **首选**：把包**同时放进用户真实桌面**（别名/重定向多的机器，
  一律读注册表 `Shell Folders\Desktop` 实测；本机存在「注册表说 D 盘、`C:\Users\<用户名>\Desktop` 也有文件」
  的双份情况 → **两个都放**），文件夹 + zip 各一份
- 直传网页只做**备用**：页面必须是一个**按钮式大链接** + 明确写出「点了没反应就打开
  `http://IP:8000/files/` 右键另存为」；`files/` 目录不放 index.html，靠 HTTP 目录列表兜底
- 包内文件名**纯 ASCII**（`fix-sync-v11.py` / `sync-watch.py` / `heal-expert.py`），
  只有给用户看的外层包名用中文 —— 因为注册表自启值和 `.bat` 正文都必须是纯 ASCII
- 告诉用户的话里必须出现**目录名 + 双击对象名**两个要素，例如
  「把桌面上的 `fix-package` 整个文件夹发到笔记本，解压后双击里面的
  `一键修复同步.bat`」

判据：**用户需要照着做的步骤数 ≤ 2，且每一步都能指出"点哪个东西"**。超过 2 步，就把它脚本化。

参考实现：`<自愈工具夹>\修复同步-v11.py` + `一键修复同步-v11.bat`
（打包时自带「`.bat` 无 >0x7F 字节 / 无控制字符」自检并打印关键路径行；
定位实现见第四节排错表「没有找到 syncthing.exe」一行）。

## 十、分级修复阶梯（定版）

**背景**：一条 `remote device missing in cluster config` 的死循环，按「把 folders 的
`devices` 整段重写」修完**仍然是死循环**，而 `folder.label` 时间线已证明写入确实生效。
此时不能再"猜着再改一遍"，必须**取证 + 分级递进**，每级都实测，通了就停。

### 10.1 取证先行（不做取证就别动手）

一次性打全，缺一项就会再绕一圈：

| 要打的 | 从哪来 | 为什么必须 |
|---|---|---|
| 所有同步进程的**完整命令行**、PID/PPID、exe 路径 | `wmic process` + Win32 快照**合并** | 判断有没有多实例、`--home` 到底指哪 |
| 实例**自报**的 config 文件与 db 目录 | `GET /rest/system/paths`（`config` ＝文件全路径） | 排除"我们改的不是它在用的那个配置" |
| `myID` | `GET /rest/system/status` | **一律现场读**，不写死 |
| 设备表**完整** ID（含 `len`、`untrusted`、`addresses`） | `GET /rest/config/devices` | 只看前 7 位会漏掉"同前缀不同串" |
| 每个文件夹**每一条**设备的完整 ID + `encryptionPassword` **长度** | `GET /rest/config/folders` | 见 10.2 两条致命分支 |
| **本侧 Syncthing 自己的日志** | `<home>\syncthing.log` | 之前只看对端报错，等于只看病人一面之词 |

### 10.2 源码级判据（读 `lib/model/model.go` 得到，判断"为什么发出去的那条会缺"）

发送端 `generateClusterConfigRLocked()` 构造 `folder.Devices` 时：

```go
deviceCfg, _ := m.cfg.Device(folderDevice.DeviceID)          // 全局设备表里查不到 → 零值
protocolDevice := protocol.Device{ ID: deviceCfg.DeviceID }  // 于是 ID 变成「空」
...
} else if folderDevice.EncryptionPassword != "" {            // 密码非空
    if folderDevice.DeviceID == device { ... } else { continue nextDevice }   // 整条跳过
}
```

两条致命分支：

1. **全局设备表里查不到该 ID** → 该条被发成**空 ID**，对端等于没收到这条；
2. **文件夹条目的 `encryptionPassword` 非空、且这条不是发给目标设备的** → **整条 `continue` 跳过**
   （自机那条永远不是"发给目标设备"，所以自机条目一旦带密码，就必然被跳过 → 对端必报 missing remote）。

接收端 `ClusterConfig()` 要求对**每一个** folder 同时命中 `m.id`（接收方自己）与
`deviceID`（发送方自身），缺哪个报哪个，**都是立即 return、整条连接作废**；
且**先判 remote** —— 所以"remote"这条报错也可能意味着**整个列表是空的**，不能反推"只有自机那条缺"。

### 10.3 四级阶梯（自动降级，每级等 40~45 秒实测连接）

| 级 | 动作 | 说明 |
|---|---|---|
| 1 | 整段重写设备表 + 四个文件夹（本机 myID 现场读、密码显式写 `""`、`untrusted:false`、`fsType:basic`） | 基础修复 |
| 2 | 逐个文件夹**暂停 → 恢复** | 强制重建会话、重发集群配置，比整机重启便宜 |
| 3 | `POST /rest/system/restart` **＋自动重新拉起** | **启动器带 `--no-restart`，重启后进程不会自己回来**，必须由脚本按原命令行（`serve --home <dir> --no-browser --no-restart`、`DETACHED_PROCESS｜CREATE_NEW_PROCESS_GROUP`）拉回来；拉不回来就明确告诉用户双击桌面启动器 |
| 4 | **删除并重建**四个文件夹登记（`DELETE` + `POST /rest/config/folders`） | 只动配置登记，**磁盘文件一个不动**；换掉一切"看不见的脏状态" |

第 4 级之后仍不通 → **停止盲改**，把本侧日志 + 完整 ID 取证发回来判读。

参考实现：`<自愈工具夹>\修复同步-v12.py` + `一键修复同步-v12.bat`
（取证段打在 `[0]`–`[2]`，阶梯在 `[4]`–`[8]`，报告同时写到包目录与桌面）。

## 十一、真凶确认与护栏（v1.7.0）

### 11.1 结论：9 字符的 `encryptionPassword`

2026-09-19 那场「连上 2 秒就断、一个字节都过不去」，真凶就是这个：

- 笔记本侧**四个文件夹**里，「本机自己」那条设备登记，`encryptionPassword` **长度 = 9**；
- 对端（主力机）那条 = 0（正常）；
- 清除后 `connected=True`，报错在 **15:22:10 之后彻底消失**（此前累计 990 条）。

**v11 为什么没修好**：v11 重写 device 条目时只写 `{"deviceID": ...}`，**省略了该字段**，
而 Syncthing 的 REST 会**保留旧值** —— 所以"配置看着对、错误照旧"。v12 显式写
`"encryptionPassword": ""` 才真正清掉。**教训：改配置一律显式写出要清空/要保留的字段，不要靠省略。**

口令的来路没能取证到底（最可能是有人在 Syncthing GUI 的文件夹编辑框里被浏览器
自动填充写进了那个密码输入框）。**因此护栏必须常驻，而不是修一次就完事。**

### 11.2 判定口径（一句话）

> **非 `receiveencrypted` 类型的文件夹里，出现任何非空 `encryptionPassword` ＝ 脏配置，清零。**

`receiveencrypted`（接收加密）夹的条目口令是**合法**的，不能动 —— 守卫据此排除。

### 11.3 验证手法：受控实验（比只看日志强得多）

想证明某条配置就是断连原因，**别只读日志，做一次注入实验**（受控实验步骤如下）：

1. 记下当前报错累计条数与连接状态；
2. 用 REST 把该字段**故意写成 9 字符**并 PUT；
3. 每 9 秒采一次连接状态 → 应当看到连接**很快掉**；
4. 跑守卫（或手动清空），再采 → 应当看到连接**恢复**。

本次实测：注入后 40 秒内连接掉；清零后 20 秒恢复。**因为报错方在对端，本机日志不会新增
`without the device info`（本机是发送方）—— 别因为"本机日志没报错"就以为注入无效，看连接状态。**

### 11.4 安装与体检套件

| 文件 | 作用 |
|---|---|
| `sync-watch.py` | 常驻主循环（每 45 秒）；每轮先调 `guard.py`，再按指纹决定是否调 `heal-expert.py` |
| `guard.py` | 口令与设备登记护栏；`--check` 零写入、改前 `.bak`、退出码 10 = 已修、`--report` 强制回传 |
| `heal-expert.py` | 专家五层登记（扫源包 → 补 cache 副本 → 修 ③④⑤） |
| `update-watch.py` + `更新守护.bat` | 把上面几个刷进常驻目录并重启守护（安装器） |
| `只看不装.bat` | `--check` 入口，一个字都不改 |
| `同步巡检.py` | 周检九项检查（复用 `guard.py`） |
| `自启登记.py` / `同步忽略登记.py` | 三条登录自启台账自愈 / `.stignore` 本机专属标记拦截 |
| `shconfig.py` / `shdetect.py` | 配置层与运行时自动探测（无个人路径与设备 ID） |

> **命名约定**：发布包内全部用 **ASCII 名**（`.bat` 正文必须纯 ASCII，中文会被 cmd 按字节偏移误解）。

### 11.5 ★ 交付方式：走同步通道，不给下载链接

包做好后**直接投进同步工作区**（如 `<协同目录>/加固包/`），
靠刚修好的同步通道自动送到对端；**用 `/rest/db/completion?folder=…&device=<对端>` 达到
100.00%、`needBytes=0` 来证明"确实送到了"**。用户只需在对端「打开这个文件夹 → 双击这个文件」。

**只给 URL 让人自己找下载按钮＝交付事故**（用户明确抗议过一次）；而且对端往往没有
OneDrive/网盘客户端，链接对他就是死路。**判据：用户需要照做的步骤数 ≤ 2，且每一步都有
"打开哪里／双击什么"的确切名字。**

## 十二、程序自更新：分发源（定版）

### 12.1 问题

常驻程序装在 `~/.workbuddy/sync-heal/`，**这个目录不在任何同步夹里**（夹子里有 `.watcher.lock`
与 PID、主机名日志，同步必冲突）。于是：**改好程序 → 传到对端 → 对端还是跑旧版**，
每改一次就得让人再点一次。

### 12.2 解法：把「分发源」放进同步工作区

    <工作区>\<自愈工具夹>\自愈程序\      ← 分发源（随工作区自动同步）
        guard.py / heal-expert.py / sync-watch.py
        update-watch.py    更新器：把上面三个刷进常驻目录并重启守护
        更新守护.bat        双击入口（正文纯 ASCII）
        只看不装.bat        update-watch.py --check 入口

守护 v3 起，每轮（45 秒）先跑 `maybe_selfupdate()`：

| 要点 | 约定 |
|---|---|
| 判据 | `md5(分发源)` vs `md5(常驻目录)`，**只在其一变化时写** |
| 安全门 | 取用前先 `compile()` 试编译，**编译不过一律不采纳**（日志记原因） |
| 留痕 | 覆盖前 `shutil.copy2` 存 `.bak-<时间戳>` |
| 生效时机 | `guard.py`/`heal-expert.py` **下一轮生效**（每轮都是新进程）；`sync-watch.py` **下次启动生效**（进程已加载到内存，改文件无效） |
| 留痕回传 | 写 `回传日志/程序自更新-<主机名>.md` |
| 频率 | 每轮都查；三个 20KB 文件哈希，开销可忽略 |

### 12.3 验收（必须真的看到，不能只看代码）

1. 改分发源里任一文件 → 前台短跑守护（`timeout 12 python sync-watch.py`）
2. 守护日志必须出现 `程序自更新：sync-watch.py（下次启动生效）`
3. `回传日志/程序自更新-<主机名>.md` 必须生成
4. **再跑一次**，日志应显示新版本号 —— 这才证明"取过来"的是能跑的新版，不是只复制了文件

隔离自测参考：`tests/test-自更新.py`（四个场景：有新版 / 幂等 / 坏文件拒绝 / 无分发源；
**应 17/17 通过**）。

### 12.4 仍需人点一次的那一下

分发源里的 `更新守护.bat`。**一次性**：跑过之后，以后所有程序更新都自动，不必再点。
不给这最后一次点击的办法不存在——对端的常驻目录够不着。**如实告知，不要含糊成"完全自动"。**

## 十三、周检与自动化（定版）

同步这种东西，"装好那天是好的"与"三个月后还是好的"是两件事。所以配一个**每周自动跑一次**的巡检。

### 13.1 巡检脚本

`<自愈工具夹>\同步巡检.py`

| 项 | 约定 |
|---|---|
| 用法 | `python 同步巡检.py`（体检并顺手修）／`--check`（只看不动）／`--quiet`（只打印结论） |
| 退出码 | 0 = 无需人处理；10 = 有需人处理项；2 = 环境不全（进程没跑 / 定位不到配置 / 加载不到守卫） |
| 报告落点 | 同步工作区 `<自愈工具夹>\回传日志\同步巡检-<主机名>-<时间戳>.md` |
| 复用方式 | 用 `importlib` 按路径加载 `guard.py`，复用它的定位与 REST 封装，**不重复实现** |
| 顺手修 | 口令 / 设备登记异常 → 调 `guard.py --report`；索引落后（need>0）→ 触发 `/rest/db/scan` |
| 只报告不修 | 守护进程没跑（拉起要用户双击，沙箱内起的会被回收）、专家登记缺项（要改本机登记并重启应用） |

九项检查：进程与配置定位 → 链路 → 四夹 → 对端完成度 → 设备登记与口令 → 常驻守护与自启 → 专家五层登记 → 近期报错 → 对端回传新鲜度。

### 13.2 ★ 判据上的两个坑（第一版全踩了）

| 坑 | 表现 | 正确判据 |
|---|---|---|
| **把历史报错当现行故障** | 1400+ 条 `cluster-config` 报错会一直躺在日志文件里，按「最近 N 小时」筛照样命中，于是**每周都误报**同一个已经修好的病 | 光看条数不够，要看**最后一条距今多久**：≤30 分钟才算「仍在刷」（真问题）；更早一律降级为"已停的历史遗留"，只进提示区 |
| **完成度四舍五入** | `completion=100.00%` 但 `needBytes=20413`（正在途中的小文件），被误报成"尚未传完" | 判"传完没"用 **`completion < 99.5`**，不要用 `needBytes>0`；`needBytes` 小而连接在 = 正常在传 |

另有两个显示层小坑：`tasklist /FO CSV` 的内存列形如 `"18,380 K"`，**数字自带逗号，不能按逗号切列**（改按 `","` 切）；回传日志的"新鲜度"要**排除本机自己写的文件**，否则自己的报告一落盘就把这一项永远刷成"刚刚更新"。

### 13.3 自动化

- 名称：**多机同步周检**　ID：`120bbd4d-d2b3-4ac6-98e3-d01d4a0085dd`
- 频率：**每周一 12:00**（避开已有的 7:30 / 8:30 / 9:00×2 / 11:00 几条，别扎堆）
- cwd 锚定：`<工作区>\<协同目录>`
- prompt 必须自带：背景（四夹、五层登记）、已知病灶的日志特征、执行命令、**必须写出的三件事**（连接 / need 与 errors / 专家登记）、汇报口径（正常 ≤6 行；异常译成人话＋给确切双击对象）

**为什么 prompt 必须自包含**：自动化每次都跑在全新上下文里，看不到任何历史对话。四夹名、五个登记层、对端 ID、日志特征、脚本路径，一个都不能省。**且只在主力机跑** —— 自动化是本机调度，对端不会执行。

### 13.4 人工补位（自动化够不到的两件事）

1. **对端视角**：巡检跑在主力机，看到的是"我这侧好不好"。要判定链路成立，**对端也得跑一次同一个脚本**，报告经同步回到主力机的 `回传日志\`，两边的 md 对着看才算齐。
2. **反复复发**：口令护栏每 45 秒扫一次，若某周报出"已修 N 次"，要回头看是谁在反复写 —— 多半是有人在 Syncthing 界面编辑过文件夹，浏览器把密码自动填充进了那个输入框。**护栏治标，习惯治本。**

参考实现与隔离自测（发布包 `tests/`，**合计 57/57 全绿**）：

| 测试 | 场景 | 结果 |
|---|---|---|
| `test-守卫.py` | 口令/设备登记护栏九项 | 通过 15 / 15 |
| `test-自更新.py` | 自更新四场景 | 17 / 17 |
| `test-守护.py` | 指纹触发三断言 | 3 / 3 |
| `test-专家自愈.py` | 专家五层登记四场景 | PASS 21 / FAIL 0 |
| `test-自启自愈.py` | 两条自启坏掉后自补 | 全绿 |

**改动任一常驻程序后必须重跑对应自测。**

## 十四、运维常识：哪些能关、哪些不能关（补）

用户最常问的就是"这个窗口能关吗、退出 WorkBuddy 会不会断"。逐条钉死：

| 对象 | 能不能关 | 关了同步还在吗 | 说明 |
|---|---|---|---|
| 浏览器里的 `http://127.0.0.1:8384/` | **能，随便关** | **在** | 这只是 Syncthing 的 Web 管理界面，是"仪表盘"不是引擎。关掉标签页只是不看仪表盘 |
| Syncthing 的 `syncthing.exe` 进程 | **别关** | **不在** | 它才是搬文件的引擎。关了就停传 —— 其余一切正常，但数据不再流动 |
| WorkBuddy 应用本身 | **能关** | **在** | 同步不依赖 WorkBuddy：引擎是独立的 `syncthing.exe`，由登录自启拉起 |
| 常驻守护（`heal-expert.py` + `guard.py`） | 能关 | 在（但护栏停摆） | 独立 pythonw 进程，同样登录自启；关了只是不再自动补登记、不再清口令 |
| 电脑关机 / 休眠 | —— | **不在** | **两边都开着才走数据**。一方关着就是它不动；等它开机后自动续传，不会丢 |

三条推论：

1. **退出 WorkBuddy 不影响同步**，但影响"看到效果"：技能与专家的**文件**同步过去了，**要重启 WorkBuddy 才会加载**。所以改了专家之后的标准动作是「等对端收全 → 在对端重启应用」。
2. 笔记本外出时**不开 WorkBuddy 也照样同步** —— 只要开机、联网、`syncthing.exe` 在跑。
3. `workbuddy.db`（任务 / 空间 / 自动化三类界面数据）**有意不进同步**：带 WAL 的活跃 SQLite，跨机同步必损坏。所以对端没有你的任务列表和空间，**这是设计不是故障**，须主动说清，否则用户会一直以为"没同步过来"。

### 14.1 关机与开机：`syncthing.exe` 不需要人去管（v1.10.0 补）

用户问得最多的是"我关机的时候这个 exe 怎么办、是不是得一直开着"。逐条钉死：

| 问法 | 答复 |
|---|---|
| 关机前要不要手动关 `syncthing.exe` | **不要，也不用**。关机时系统会一并结束它。关机前手动关它没有任何好处，反而可能中断正在传的文件 |
| 关机了同步是不是就断了 | 是。**两机同时开机且联网才走数据**。一方关着，那一侧的改动就停在那里，等它开机后自动续传，**不会丢、不需要重传** |
| 是不是得 24 小时不关机 | **不必**。它只在机器开着的时候工作。关机 = 暂停，开机 = 接着走 |
| 开机后谁会把它拉起来 | **登录自启**。本机两条登记：① 启动文件夹里的 `启动同步-Syncthing.bat`（纯 ASCII、路径已烤入）；② 注册表 `HKCU\...\Run` 的 `ZGH-SyncHeal`（守护，用 `pythonw.exe` 无窗口）。**登录后自动就位，不用点任何东西** |
| 打开 WorkBuddy 会不会自动起同步 | **不会**。两者毫无联动。Syncthing 是独立进程，靠登录自启，不靠 WorkBuddy |
| 退出 WorkBuddy 会不会把同步关掉 | **也不会**。退出 WorkBuddy 后同步照常跑，文件照常搬；只是 WorkBuddy 不再加载新到的东西，**重新打开才生效** |
| 怎么确认自启真的生效了 | 重启后跑一次 `同步巡检.py`，看「常驻守护与自启」那一项；再确认 `tasklist` 里 `syncthing.exe` 有两个进程（父子对，正常） |

> 容易误解的一点：`127.0.0.1:8384` 那个页面开不开、关不关，与同步**没有任何关系**；`syncthing.exe` 在不在，才是唯一要紧的事。**别把"关了网页"当成"关了同步"，也别把"退出 WorkBuddy"当成"停了同步"。**

### 14.2 ★ 「感觉没在同步」的第一顺位排查：自启哑了半边（2026-09-22 实测）

**背景**：用户说"已经在同步"，但两边文件其实**一个字节都没动**，而且**没有任何报错**。

**取证四步（照这个顺序，别跳）**：

| 步 | 查什么 | 判据 |
|---|---|---|
| 1 | 枚举进程（`CreateToolhelp32Snapshot`） | `syncthing.exe` **一个都没有** ⇒ 引擎没起来，后面都不用查了 |
| 2 | 读**真日志** `data\syncthing.log` 尾部 | 有 `INF Exiting` 但下一次开机后**无任何启动记录** ⇒ 就是自启没拉起来 |
| 3 | 逐条核三条自启 | 见下"半边哑"判据 |
| 4 | 日志按天统计 | 出现**断档日**（行数与同步动作骤降）⇒ 确诊"用户感受"的来源 |

**★ "半边哑"关键判据（本轮最值钱的一条）**：

> **注册表 `HKCU\...\Run` 的两条起来了、启动文件夹那条没起来 ⇒ 单独指向"启动项被清理"，而不是整个自启机制崩了。**

本轮实测形态：

| 自启项 | 登记处 | 状态 |
|---|---|---|
| `ZGH-SyncHeal`（守护） | `HKCU\...\Run` | ✅ **进程活着**（pythonw） |
| `ZGH-ExpertSelfHeal`（heal-expert.py） | `HKCU\...\Run` | ✅ 已登记 |
| `启动同步-Syncthing.bat`（**引擎**） | **启动文件夹** | ❌ **文件在、602 B、纯 ASCII 全对，但没被执行** |

两条注册表 Run 生效、唯独启动文件夹那份失效 —— 这正是**"开机加速"类工具清理启动项**的典型指纹
（它们普遍只扫启动文件夹）。**所以：引擎没起来时要先看启动文件夹那份，别只查注册表。**

**推论（反直觉但重要）**：
- 守护进程活着 **≠** 同步在跑。守护只管"专家登记 + 口令护栏"，**它不搬文件**。
  本轮就是"守护活得好好的、引擎死着"，界面与日志都不报错 —— **最阴的一类故障**。
- 所以"两边不同步"**不等于**"同步配错了"。先确认引擎在不在，再谈配置。

**处置**：让用户双击 `启动同步.bat`（沙箱内起的会被回收，见踩坑表），当场恢复。
**长期**：这正说明第十六节"自启自愈"必须覆盖**启动文件夹那一份**，不能只核注册表。

## 十五、任务收尾：残余清理（定版）

多机同步这类任务会留下一大堆"一次性材料"：探针脚本、打包暂存、逐版指令、桌面分发件、直传服务内容物、`.bak`、`__pycache__`。它们**在同步夹里**，不清就会同步到对端、拖慢索引、也让下一次排查时真假难辨。以下是清理时的判据与纪律。

### 15.1 四分类判据（先分类，再动手）

| 类 | 特征 | 处置 |
|---|---|---|
| **甲 · 机制部件** | 常驻程序、巡检脚本、分发源、回传日志目录 | **必留**，一个不能删 |
| **乙 · 自测脚本** | `tests/test-*.py`，本技能正文引用了它们 | **必留**，改程序后要靠它复验 |
| **丙 · 正式产出物** | 逐版修复脚本、报告、指令 md、留档清单 | **移入归档子目录**，不删（版本铁律） |
| **丁 · 一次性材料** | 探针/查询脚本、打包暂存目录、`.bak-*`、`__pycache__`、过期 zip/rar、桌面分发件 | **删** |

**甲类必须钉死（删了会断链）：**

| 文件 | 谁在引用它 |
|---|---|
| `<协同目录>\heal-expert.py` | `自启登记.py` 写的自启项 `ZGH-ExpertSelfHeal` **直接指向它** —— 删了自启就断 |
| `guard.py` / `sync-watch.py` / `同步巡检.py` / `自启登记.py` / `同步忽略登记.py` | 常驻守护与周检自动化调用；`同步巡检.py` 用 `importlib` 加载 `guard.py` |
| `自愈程序\`（`guard.py` / `heal-expert.py` / `sync-watch.py` / `update-watch.py` / 3 个 bat） | 程序自更新的**分发源**，守护每轮比对它取新版 |
| `回传日志\` | 两机互查的日志通道 |
| `tests/test-守护.py` / `test-守卫.py` / `test-自更新.py` / `test-专家自愈.py` / `test-自启自愈.py` | 本技能第十三节点名引用 |

### 15.2 动手前的三道闸

1. **先查引用，再判生死**：删任何 `.py` 前，`grep` 一遍注册表值、本技能正文、`update-watch.py` 的分发清单、其他脚本里的路径常量。**被引用的不进删除清单。**
2. **先量体积，再报数字**：清理说明里写体积必须是**实测**（`sum(os.path.getsize)` 递归）。曾凭印象说某临时目录 7 KB，实际 4,272 个文件 / 159 MB —— 这类数字错了会让用户对整份清单失去信任。
3. **删除用白名单**：**逐个列举文件名**，绝不用"保留清单 / 黑名单"式批量删（漏一项就误删正式产出）。本机 `os.remove` / `Remove-Item` **不进回收站、不可逆**，执行前把清单落盘留档（如 `删除记录-<事由>-<日期>.txt`）。分批 ≤10 个，每批核一遍。
4. **执行器必须幂等，且绝不能只信它自报的计数**：清理脚本被重复触发时（沙箱重试、用户双击两次、命令回显丢失后重跑），第二次看到的源已被移走，于是**每一项都落进"跳过"，归档数、备份数全变 0**，而磁盘上其实早已搬完。**报出的"0 项"会让人误判成失败并再折腾一轮。** 正确做法：① 脚本按"源在才动、不在就跳过"写，天然幂等；② 复验**一律回到磁盘列目录看实际状态**（归档目录几项、备份目录几项、机制部件是否在位），脚本计数只作参考；③ 明细若被第二次运行写空，按磁盘实际内容补一份 `-明细补充` 记录，别去改主记录。

### 15.3 同步夹清理的特殊后果（与普通目录不同）

- 同步夹内的删除**会同步到对端** —— 这是期望效果，但要确认对端没有"只在那边存在"的同名文件。只清**本机自己产生、且对端确认不再需要**的东西。
- 对端的桌面 / 部署包目录**够不着**，那边要清得在对端单独操作，**不要承诺"我这边清了那边就干净了"**。
- 清完跑一次 `同步巡检.py --check` 复验（退出码 0 = 无需人处理），报告落 `回传日志\`，让这次清理有据可查。
- `__pycache__` 已在 `.stignore` 内（不进同步），清它只为省本地空间与免干扰排查。

### 15.4 归档优于删除的边界

- **要归档**：逐版修复脚本、逐版指令 md、修复/加固报告、操作卡 html —— 它们记录"当时为什么这么改"，是下一次复发的第一手材料。
- **可直删**：`写日志-*.py`、`查状态-*.py`、`查日志*.py`、`打包*.py` 这类**只为生成某一段文字或读一次状态**而存在的一次性脚本；`_pkg_*` 打包暂存；`*.bak-*`；过期 `zip`/`rar`；桌面上的分发件副本。
- **别删错**：`删除记录-*.txt`（留档）、`自愈日志-*.md`（回传日志）、`.stfolder`（Syncthing 标记目录）、`<同步工具目录>\versions\`（版本历史仓库）—— 看着像杂物的都不是。
- **桌面分发件要连"真桌面"一起清**：本机真桌面在 D 盘（见第六节踩坑），且上面往往留着一整排 `.bat`/`.url`/`.lnk` —— 那些是用户的**按钮**，删之前先读内容判断是不是入口，别当分发件一起扫掉。

## 十六、登录自启也要能自愈（定版）

### 16.1 为什么单独立这一节

文件同步自愈了、专家登记自愈了，但**"把程序拉起来"这件事**一直是盲区。
三条登录自启是登记在 Windows 里的，**被安全软件、"开机加速"清掉时不会有任何提示** ——
表现只是「某天开始两边不同步了」。排查的人如果只查 Syncthing 配置、设备登记、磁盘，
**一条都对不上**，因为根因根本不在那儿。

结论：**自启必须是自愈项，而不是"装机时登记一次就完事"。**

### 16.2 三条自启的台账

| # | 登记处 | 拉起的程序 | 作用 |
|---|---|---|---|
| A | 启动文件夹 `启动同步-Syncthing.bat` | `syncthing.exe` | 同步引擎 |
| B | `HKCU\...\Run` → `ZGH-SyncHeal` | `sync-heal\sync-watch.py` | 常驻守护（每 45 秒巡专家登记 + 口令） |
| C | `HKCU\...\Run` → `ZGH-ExpertSelfHeal` | `heal-expert.py` | 开机自检专家五层登记（本轮起也核自启） |

**三者都能免管理员写**（启动文件夹在自己家目录、`HKCU` 是当前用户）——
这是选它们、不选计划任务的关键理由之一：**自愈动作不需要提权**。

### 16.3 实现：一个共用模块 + 两个入口

新增 `<自愈工具夹>\自启登记.py`：`audit(dry=True/False)` → `{ok, fixed, issues, notes}`，
`--check` 零写入、修复模式退出码 10。由两个入口调用，**双保险**：

| 入口 | 何时跑 | 覆盖 |
|---|---|---|
| `heal-expert.py` 第 ⑥ 节 | **每次开机**（它自己就是自启项 C） | 三条全核，缺了补 |
| `同步巡检.py` 第 6 项 | **每周一 12:00**（自动化「多机同步周检」） | 同上，并落 `回传日志\` |

它是**分发源里的普通文件**（`自愈程序\自启登记.py`），随工作区同步到对端。
因此 `sync-watch.py` 的自更新清单与 `自愈程序\update-watch.py` 的 `FILES`
**都要显式加上它**，否则对端取不到、`heal-expert.py` 找不到这个模块。

设计纪律（每条都是踩出来的）：

1. **判据看"功能"不看"字节"**：判定启动器要不要重写，只看"它写的 `SYNC_ROOT` 下确有 `syncthing.exe`"，
   **不比对注释文字**。第一版逐字节比对，注释差几个字就判"过期"，于是每次都重写一遍。
2. **注册表判定看"指向的脚本是否存在"**，不看是否等于某个固定串 ——
   否则两台机器各自算出的"标准答案"不同，会来回改写。
3. **拿不到目标路径时只报告、绝不乱写**（找不到 `syncthing.exe`、或路径含非 ASCII 时都不动）。
4. **启动器必须纯 ASCII**（老账：cmd 按字节偏移跳行）。
5. **写回保持原形态**（`list` 就 `list`、`dict` 就 `dict`，见 16.4）。

### 16.4 ★ 顺手挖出的两个真 bug

**(1) `installed_plugins.json` 单条记录可能是 `dict` 而不是 `list`。**

72 条里 **71 条是 `list`**，被应用重写过的那条是 **`dict`**：

```json
"<专家名>@my-experts": {
  "scope": "user", "installPath": "…\\cache\\my-experts\\<专家名>\\1.39.1",
  "version": "1.39.1", "lastUpdated": "2026-09-19T16:45:15"
}
```

`heal-expert.py` 原来只写 `entries = inst["plugins"].get(key) or [{}]` 再取 `entries[0]`
→ 遇 `dict` 直接 **`KeyError: 0`**。而这条恰好是本方专家那条，
**等于"开机自愈"一直跑不完整，却因为崩在 `--check` 之外没人发现**。

正解：读的时候 `list`/`dict` 都认，写回时**保持原形态** —— 不去改应用自己的约定。

**(2) 真实桌面不一定是 `C:\Users\<用户名>\Desktop`。**

本轮按 `C:\Users\<用户名>\Desktop` 去清桌面、还报告"桌面已清空"，
其实那是个**空壳**；真桌面在 `D:\Users\<用户名>\Desktop`，
里面 11.39 MB 分发件原封未动。**纪律：动用户目录前先从注册表查真实路径。**

```python
import winreg
k = winreg.OpenKey(winreg.HKEY_CURRENT_USER,
    r"Software\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders")
winreg.QueryValueEx(k, "Desktop")[0]                                  # 桌面
winreg.QueryValueEx(k, "Personal")[0]                                 # 文档
winreg.QueryValueEx(k, "{374DE290-123F-4565-9164-39C4925E467B}")[0]   # 下载
winreg.QueryValueEx(k, "My Pictures")[0]                              # 图片
```

本机实测：**四项全在 D 盘**。

实测：`已修 2 项`、退出码 10、两条都补回。

### 16.6 桌面应急按钮收纳（定版）

**用户诉求**：把桌面 4 个手动按钮收进文件夹，桌面保持清爽（"重度洁癖"）。
**结论：可以收，零风险** —— 但要先做一次「相对路径体检」，不能凭感觉说没问题。

**① 动手前必做：相对路径体检。**

桌面按钮脚本里若存在 `.\` 或 `..\` 引用（读同目录的配置、图标、数据），
一移走就失效。体检脚本 = 逐个读 `.bat` / `.cmd` / `.url` 的字节，
正则找 `(?<![\w:.])\.\.[\\/]|(?<![\w:.])\.\\`，命中数必须为 0 才可移。

本机实测四个按钮**绝对路径引用 100%**，相对引用 0 处 → 随便放：
`<同步工具目录>\syncthing`、`C:\...\sync-heal\sync-watch.py`、`http://127.0.0.1:8384`、`<同步工具目录>\share`。

**② 移图标不影响登录自启。**

自启靠启动文件夹 + `HKCU\...\Run`，与桌面图标**零关联**。
移完必须跑 `自启登记.py --check` 复验（应仍 3 项全绿）——别只说"不影响"，要给证据。

**③ ★ 中文目录名会逼出 `.bat` 的编码坑（本轮新踩）。**

想写个「打开工具箱.bat」入口，若目录名是中文，正文就含非 ASCII，双击找不到目录。
四条路，按推荐度排序：

| 方案 | 可行性 | 说明 |
|---|---|---|
| **目录改半角名** | ★ 首选 | 桌面是私人区域、不参与同步，改名零代价。`WorkBuddy-Sync` / `Desktop-Tools` |
| 8.3 短名（`GetShortPathNameW`） | ✗ 本机不可用 | 实测该机**未开启 8.3 短名**，返回的短名仍是中文 |
| `for /f` 遍历目录名 | ✗ 不要用 | 匹配逻辑脆弱，写起来绕且易错 |
| 正文写中文字节 | ✗ 禁止 | 老账：cmd 按字节偏移解析 `.bat` |

**纪律**：不要为了"不打扰用户"硬凑纯 ASCII 绕路（短名、遍历都是绕路，且本机走不通）；
**改个目录名是最省事、最可靠的正解**，只需向用户说明"桌面这个文件夹不参与同步，改名无副作用"。

**④ 收纳后的定版形态**（本机已落地）：

```text
桌面/
  打开同步工具箱.bat        ← 唯一入口，正文 166 B 全 ASCII：

```

用 `%~dp0` 而非写死盘符 —— 盘符变了还能用。

**⑤ 版本铁律适用于按钮**：入口按钮迭代产生的 `.v1` / `.v2` 不要删，
移入 `归档-<日期>\`。本轮 `打开同步工具箱.bat.v1`（双重编码 bug 版）、
`.v2`（退路版）均已归档。

**⑥ 交付话术**：用户洁癖，只关心"桌面能不能变少"。直接给数字——
**"桌面可见项从 5 个降到 2 个（`desktop.ini` 是隐藏的系统文件）"**，
再说明"原来的按钮都在 `WorkBuddy-Sync` 里，双击桌面那个入口就能打开"。

## 十七、怎么用数据回答「到底在不在同步」（定版）

用户问"我感觉没在同步"时，**别用"我看是好的"回答** —— 要给能自查的数字。
`同步巡检.py --check` 全绿只是必要条件；**全绿 ≠ 在动**。以下是本次实证的判读法。

### 17.1 四处取证，缺一处就可能误判

| # | 取证点 | 怎么取 | 说明 |
|---|---|---|---|
| 1 | **链路类型** | `/rest/system/connections` 的 `type` | `tcp-client` = 直连；`relay` = 走中继（慢，但也是通） |
| 2 | **双向字节增量** | 同上，隔 15~20 秒采两次看 `inBytesTotal` / `outBytesTotal` | 但 **Syncthing 心跳间隔 90~120 秒**，20 秒内为 0 **不等于**断了 —— 只说明"此刻没有要传的数据"，**不能单独作判据** |
| 3 | ★ **待传量的变化**（最硬） | `/rest/db/completion?folder=X&device=<对端>` 的 `needBytes`，隔 20 秒连采 5 次 | **降 = 对端正在拉走**；涨 = 本机正在产生新东西；**一动不动才是真卡住** |
| 4 | **本机缺不缺** | `/rest/db/status?folder=X` 的 `needFiles` / `errors` / `state` | `needFiles=0`+`state=idle` = 本机不欠；非 0 才要查接收侧 |

**判读口诀：不看快照看趋势。** 单次读数没有意义（8 MB 待传看着像卡住，实际是在途）。

### 17.2 实测样本（2026-09-21 主力机视角）

```text
08:58:02  wb-skills 待传 170,943  →  08:59:42  wb-skills 待传 0
```

**100 秒内 170 KB 被拉走 → 这就是"对端在工作"的铁证**，比任何日志都直接。

同一时间 `my-workspace` 待传从 8.0 MB 涨到 8.37 MB —— 涨**不是故障**，
是本机（诊断脚本、自动化、日常编辑）在往同步夹里写东西，属"自产自销"。
**判断积压要配合 `localFiles` vs `globalFiles` 一起看。**

### 17.3 ★ 日志按天统计：一眼看出"断档"（本次的关键手法）

```python
by_day = Counter(); synced = Counter()
for l in open(log).read().splitlines():
    if re.match(r"\d{4}-\d{2}-\d{2}", l[:10]):
        by_day[l[:10]] += 1
        if "Synced file" in l or "Updated file metadata" in l:
            synced[l[:10]] += 1
```

实测结果（本机 `<同步工具目录>\syncthing\data\syncthing.log`）：

| 日期 | 日志行数 | 同步动作行 |
|---|---|---|
| 09-19（周六） | 6240 | 507 |
| **09-20（周日）** | **52** | **38** |
| 09-21（周一） | 40 | 23 |

**用户"感觉没在同步"的直接来源就是 09-20 这个断档** —— 笔记本那天没开机（第十四节：
"两机同时开机且联网才走数据"）。**要在报告里主动指出断档日，并说明数据不丢、开机自动续传**，
否则用户会以为出了故障。

### 17.4 ★ 抖动源识别：`Counter` 统计被反复同步的文件

```python
cnt = Counter()
for l in lines:
    if "Synced file" in l or "Updated file metadata" in l:
        m = re.search(r"file\.name=([^ ]+)", l)
        if m: cnt[m.group(1)] += 1
```

实测 TOP（两天内）：

| 次数 | 文件 |
|---|---|
| 43 | `ppt-beautify\_skillhub_meta.json`、`ai-intelligence-investigator\_skillhub_meta.json`、`ai-lawyer-contract-review\_skillhub_meta.json` |
| 42 | 上述三个的 `_icon.jpg` / `_icon.svg` |
| 30 | `summarize__skillhub` / `self-improving__skillhub` / `ontology__skillhub` 的 `_icon.png` + `_skillhub_meta.json` |

**成因**：WorkBuddy 检查市场技能更新时重写这几类文件的 `_icon` 与 `_skillhub_meta.json`。
**不是故障**（不影响正确性），但会让"索引一直在忙"看起来像"没同步完"。
**结论话术**：这是噪音源，不是故障；不必处理。

### 17.5 ★★ 真 bug：`wb-experts-cache` 缺 `.stignore`，本机进程锁文件在跨机同步

**症状**：`wb-experts-cache` 里出现 `<专家名>\<版本>\.in_use\<PID>` 与
`.orphaned_at` 被同步，并**实时制造冲突副本**：

```text
<专家名>\1.39.1\.in_use\2208.sync-conflict-20260921-081807-<对端ID>
                                                      ↑ 产生于今早 08:18，<对端ID> = 对端
```

**实测规模**：`.in_use/` 内 **101 个** PID 文件、`.orphaned_at` **5 个**（合计仅 8.8 KB，
体积毫不可观 —— **所以它不会被"体积"这类指标发现，必须专门查**）。

**危害**：
1. `.in_use/<PID>` 是**本机进程占用标记**，对端收到后可能误判"某个旧版本仍在使用"；
2. 两端 PID 空间重叠 → **同名不同源 → 持续产生 `sync-conflict` 副本**；
3. 属第十节 `wb-experts-cache` 一切"看不见的脏状态"的稳定来源。

**为什么之前没发现**：它不报错、不占空间、不显示在完成度里（四个夹照样 100%）。
是"查抖动源"这个动作把它揪出来的。

**修法**（完整处置已做成共用模块 `同步忽略登记.py`，见**第十八节**）：
在 `wb-experts-cache` 夹根建 `.stignore`，写入三条
（`(?d).in_use` / `(?d).orphaned_at` / `(?d).created-by-session`）。
**★ 三条都必须带 `(?d)` 前缀** —— 缺了它，对端删除某个目录时本机会因
"目录里只剩被忽略的文件"而拒绝删除，整个夹永久卡在「未同步」（见**第二十一节**）。

> **★ 写入方式已更正（2026-09-21 实测，推翻本节旧写法）**
>
> 旧写法建议「写临时文件 → `os.replace` 原子替换」。**这是错的，别再用。**
> `os.replace` 确实能成功，但它会把目标文件**整份换掉**——实测中把 582 B 的完整规则
> 覆盖成了 7 B 的测试串（靠备份才救回来）。而且 Syncthing 自己也在读写这个文件，
> 存在 `PermissionError` 抢占窗口（实验里真撞上过）。
>
> **一律改走 Syncthing 官方接口**：`GET /rest/db/ignores?folder=X` 读全量 →
> 内存里合并缺失行 → `POST /rest/db/ignores?folder=X` 写回 → 复读校验 →
> `POST /rest/db/scan?folder=X` 重扫。代码与完整流程见第十八节。

**纪律**：
- **不要删正在使用的 `.in_use`**（1.39.1 里那个是活进程的锁）；`.stignore` 只是**不再同步**它们，
  本地文件照旧。
- 加了 `.stignore` **不会自动删除已经同步到对端的那些**，对端残留需单独处理，
  或任其自然（它们已不参与后续同步）。
- **同类风险要一并排查**：凡是**每机不同、含 PID/主机名/绝对路径**的运行时产物，
  都不该进同步夹。已知清单：`.in_use/`、`.orphaned_at`、`.stfolder`（Syncthing 自己会排除）、
  `workbuddy.db`（红线 1）。

### 17.6 报告口径（照这个结构写，用户才看得懂）

1. **一句结论 + 证据**：在同步 / 不在同步，附"待传量 XX 秒内从 A 降到 B"这类数字；
2. **解释感受从哪来**：断档日 + 抖动源，逐条给数据；
3. **点出真问题**：`.in_use` 跨机同步 + 已有冲突副本，说明危害与修法；
4. **给自查动作**：双击桌面 `查看同步状态.url` → 看设备在不在线、字节数涨不涨；
5. **问是否动手**：改同步夹配置会影响对端，**先报告再动手**。


## 十八、同步忽略登记：让「本机专属标记」不再跨机（定版）

### 18.1 病症与真实代价（比"多几个冲突副本"严重得多）

`wb-experts-cache`（运行副本夹）里有一批**每机不同**的小标记。它们跨机同步时会：

1. 两台机器进程号一撞名 → 产生 `xxx.sync-conflict-日期-设备ID` 副本；
2. **更严重**：对端删这类文件时，本机那份正被进程占用删不掉 →
   Syncthing 报 `Failed to sync … file modified but not rescanned` →
   **`Folder failed to sync, will be retried (wait=1m0s)` —— 整个文件夹同步失败并反复重试**。

实测证据（`<同步工具目录>\syncthing\data\syncthing.log`）：

```text
2026-09-19 17:12:44  path=<专家名>\1.39.1\.in_use\25568
2026-09-21 08:18:06  path=<专家名>\1.39.1\.in_use\2208
                     error="syncing: delete file: file modified but not rescanned"
                     INF Folder failed to sync, will be retried (wait=1m0s …)
```

它天天可能发生，但**不报错、不占空间、完成度照样 100%** —— 只有翻日志才看得见。

### 18.2 官方机制三条（查文档得来，不是推测）

| 机制 | 结论 | 对处置的影响 |
|---|---|---|
| `.stignore` **永不跨机传输**（"will never be synced to other devices"） | 每台机器都必须**各自配一份** | ★ 这是"对端还要不要再做一次"的答案：要 |
| 被忽略的文件**默认不会被删除**（不加 `(?d)` 前缀） | 两边各自的文件原样留着 | 忽略 ≠ 删除，不会波及对端已同步的那份。**但父目录被删时会连带卡住，所以规则表里一律写 `(?d)` 形式** —— 见第二十一节 |
| 规则不含 `/` 时匹配**任意层级**的同名文件/目录 | `.in_use` 一条即可覆盖各版本目录 | 不必逐个版本写 |

### 18.3 该拦哪些：一条判据

> **内容每机不同（PID / 时间戳 / UUID / 绝对路径）＝ 本机专属 ＝ 该拦。**
> 内容跨机应当一致（插件元数据、包本体）＝ 正经内容 ＝ 一律不拦。

| 名字 | 是什么 | 拦？ |
|---|---|---|
| `.in_use` | 目录，内含以进程号命名的锁文件 | ✅ |
| `.orphaned_at` | 文件，毫秒时间戳 | ✅ |
| `.created-by-session` | 文件，本机会话 UUID | ✅ |
| `.codebuddy-plugin` | 目录，插件元数据（`plugin.json`） | ❌ |
| `.gitkeep` | 空占位文件 | ❌ |
| `.stfolder` | **Syncthing 自己的夹标记** | ❌❌ **拦了整个夹就报废** |

### 18.4 资产：`同步忽略登记.py`（共用模块 + 两个入口）

| 项 | 做法 |
|---|---|
| 写入通道 | **只走 Syncthing API**：`GET /rest/db/ignores` → 合并缺失行 → `POST` → 复读校验 → `POST /rest/db/scan` |
| 幂等判据 | **只看必需 pattern 是否独立成行存在**，不比对注释文字；不缺则不写、不动已有内容 |
| 接口 | `audit(dry=True/False)` → `{ok, fixed, issues, notes}`（与 `自启登记.py` 同款四类） |
| 命令行 | `python 同步忽略登记.py --check`（只读）／不带参数（自动补） |
| 接入 | `heal-expert.py` 第 **⑦** 段（开机）＋ `同步巡检.py` 第 **[10]** 项（周检） |
| 分发 | 源在工作区根 → 铺到 `自愈程序\`（分发源）＋ `sync-heal\`（运行副本），**逐文件哈希校验** |
| 自更新列表 | `sync-watch.py` 的复制列表、`update-watch.py` 的 `FILES` 三处都要加 |

### 18.5 ★ 对端怎么办（用户原话：会不会反而造成无法同步）

**会不会？** 不会。规则只匹配那三个名字，其余文件照常同步；被忽略的文件也不会被删。
反过来——**不修才会让整个文件夹同步失败**（18.1 的日志就是证据）。

**为什么单边配不够？** 对端不知道本机的忽略列表（`.stignore` 不传输），
它会一直认为"本机缺这些文件"并反复尝试推送。所以两边都配才干净。

**对端两条路：**

| 路 | 做法 | 适用 |
|---|---|---|
| **A·长线自动** | 自愈（开机）与巡检（周检）会自己核、自己补 | 新脚本已经到对端之后，**永久有效** |
| **B·立即兜底** | 工作区 `<自愈工具夹>\对端修复-同步忽略规则\` → 在对端**双击** `RUN-ME-fix-sync-ignore.bat` | 新脚本还没轮到对端时，**用一次** |

**★ 鸡生蛋：新模块怎么到对端（本轮实遇，必须留兜底）**

对端跑的是**旧守护**，它的复制列表里没有 `同步忽略登记.py`。结果：
新版 `heal-expert.py` 会被正常取走（列表里有它），但**新模块取不过去**，
新脚本执行到第 ⑦ 段只能"找不到模块，跳过" —— 看着铺开了，实际空转。

破解（已实现）：给 `load_sync_ignore()` 多加**工作区兜底候选**：

```python
for base in (os.environ.get("ZGH_SELFHEAL_LOGDIR"),
             os.environ.get("ZGH_WORKSPACE"),
             r"<WORKSPACE>\<COOP_DIR>"):   # 已实测两机路径一致
    cands.append(os.path.join(base, "同步忽略登记.py"))
    cands.append(os.path.join(base, os.pardir, "同步忽略登记.py"))
```

模块在工作区里一定有（随 `my-workspace` 同步过去），所以即便对端 `sync-heal\` 里缺它，
新版 `heal-expert.py` 也能就地找到并执行。

> **通用纪律**：凡「运行副本里可能还没有」的共用模块，加载器一律**带工作区兜底候选**。
> 只认脚本自己所在目录，就会卡在这种先后顺序里。

**通道确实在动（实测证据）**：对端回传日志 `回传日志\程序自更新-<主机名>.md` 记下

```text
## 2026-09-21 09:24:09
- 来源：`<工作区>\<协同目录>\自愈程序`
- · `heal-expert.py` —— 下一轮生效
- · `sync-watch.py` —— 下次启动生效
```

即：**主力机一改完分发源，对端 45 秒内就取走了** —— 往对端推新脚本不必手工搬运，
要人工的只有"对端同步夹的配置"这一类（`.stignore` 不跨机）。

B 包设计要点：
- `.bat` 正文**纯 ASCII**（0 个非 ASCII 字节），行尾 CRLF；
- 用 `for /d` 扫 `%USERPROFILE%\.workbuddy\binaries\python\versions\*` 自动找 Python（两台机器用户名不同也适配）；
- `pushd "%~dp0"` 后用**相对文件名**调 .py —— 不让中文路径经命令行传递；
- 脚本**独立实现**（不依赖别的模块），走 API 写入；
- 跑完在包目录留 `修复结果-<主机名>-<时间>.txt`（UTF-8 中文）→ **自动同步回主力机**，
  下次这边就能确认对端到底修没修成。

### 18.6 ★ 三个真踩坑（本轮新增，都是自己撞的）

**① 探查脚本禁止对真实目标做破坏性写入 —— 我用 `os.replace` 把生产配置覆盖了**

为了"验证原子替换是否可行"，探查脚本真对 `my-experts\.stignore` 执行了
`os.replace(tmp, IG)` → **582 B 九行规则被覆盖成 7 B 的 `probe`**。
靠实验前自动备份的文件恢复（`归档\stignore-备份-*.txt`）。

> **纪律**：验证写操作**只在副本上做**；真实目标一律走 API。
> 探查脚本里凡带 `os.remove / os.replace / shutil.move` 且指向真实路径的，写之前先问一句"这一步是破坏性的吗"。

**② `POST /rest/db/scan` 的 body 不能丢给 `json.dumps`**

传 `body=b""` → `TypeError: Object of type bytes is not JSON serializable` →
而它被上层 `try/except` 吞掉 → **重扫从未真正执行**（一直靠 fsWatcher 兜着，所以没人发现）。

```python
# 正确写法：bytes 直接用，别序列化
if body is None:            data, ctype = None, False
elif isinstance(body, (bytes, bytearray)):  data, ctype = bytes(body), False
else:                       data, ctype = json.dumps(body).encode("utf-8"), True
```

**③ 直接写 `.stignore` 真的会撞 `PermissionError`**

实验里真撞上过（Syncthing 正在读写该文件的窗口期）。
所以"走 API"不只是规范问题，是**能不能稳定写进去**的问题。

### 18.7 验收顺序（照这个做，别只看代码说"能自愈"）

1. `同步忽略登记.py --check` → 先报告"缺什么"（**验证查得出**）；
2. 走 API 造出"缺一条"的状态 → `audit(dry=False)` → 复读三条齐（**验证补得上**）；
3. 幂等复跑 → `fixed` 为空（**验证不反复动**）；
4. **兜底还原**：`finally` 里把原始规则 POST 回去，复读与原始一致；
5. 终检：四夹 `state=idle / needFiles=0 / errors=0`，且**忽略规则写入后日志 0 条 ERR/WRN**；
6. 端到端：用**运行副本**（`sync-heal\heal-expert.py --check`）跑一遍，
   确认它在真实运行位置能找到新模块（模拟开机自愈场景）。

## 十九、工作区改名：五处都要改，漏一处就是「列表在、点开空」（定版）

**触发**：你要把同步的工作区文件夹改名（例如 `<旧名>` → `<新名>`），两台机器都要改。

### 19.1 ★ 会话正文不在数据库里（本节唯一重点）

数据库（`~\.workbuddy\workbuddy.db`）只存会话的**目录卡**：
`workspaces.path`、`sessions.cwd / title / created_at`、`automations.cwds`。
**正文一个会话一个文件**，在应用数据中枢：

```text
%USERPROFILE%\.workbuddy\projects\<工作区路径编码>\<会话id>.jsonl
```

**路径编码规则**：盘符小写 ＋ 各级目录用 `-` 连接。
`E:\<旧名>\06-每日行业新闻` → `e-<旧名>-06-每日行业新闻`。

只改数据库、不改这个目录名，程序按新路径找正文**一个都找不到** ——
**会话列表还在（数据库给的），点开全是空的（目录给的）**。
实测一次改名后 **99 条会话只对上 72 条**，工作区根目录那 27 条全部对不上。

**判据**：改名后如果「列表在、点开空」，先比对
`SELECT id, cwd FROM sessions WHERE cwd LIKE '%<新名>%'` 与
`projects\<编码>\<id>.jsonl` 的存在性，**一条不许缺**。

### 19.2 六处清单（按此顺序，缺一不可）

| # | 改什么 | 位置 | 是否每台都要做 |
|---|---|---|---|
| 1 | 工作区文件夹名 | `<盘符>:\<旧名>` → `<盘符>:\<新名>` | 两台 |
| 2 | 工作区里文件内容中的路径文字 | 脚本 / 配置 / 技能 / 专家包 | 只主力机（靠同步传过去） |
| 3 | 数据库 `workspaces.path` / `sessions.cwd` / `automations.cwds+prompt` | `~\.workbuddy\workbuddy.db` | **两台** |
| 4 | **会话转录目录名** | `~\.workbuddy\projects\<旧编码>*` → `<新编码>*` | **两台 · 不参与同步** |
| 5 | 自愈配置里的工作区路径 | `~\.workbuddy\sync-heal\guard-config.json` 的 `workspace` | **两台** |
| 6 | **同步工具自己 `config.xml` 里那个夹的 `path`** | 各机不同，**一律从第 5 条 `guard-config.json` 的 `config_xml` 字段反查** | **两台 · 必须关着同步进程** |

**为什么 1/3/4/5/6 全都要两台各做一遍**：**同步只传文件内容、不传文件夹名**，
也不传各机本地的配置。任何"本机配置类"的改动都不会自动过去。

第 4、5 两条最容易漏。第 5 条漏了是**静默失效**（守卫从此盯一个不存在的路径，不报错）。
第 6 条漏了的现场表现极具迷惑性 —— 见 19.4。

### 19.3 ★ 必须关着客户端做（含改名目录）

三条都要求客户端退出：数据库被锁、会话工作目录就在被改的文件夹里、
**正在打开的会话其正文文件被进程占着**（改目录名报「拒绝访问」，错误信息会点名到具体 `.jsonl`）。

现场表现：目标目录**不存在**时（全新建）改名能成；目标**已存在**时（并入）会因目录被占而失败。
所以脚本要写成「**逐文件移动 + 失败点名 + 可重复执行**」，不要一句 `os.rename` 赌到底。

### 19.4 ★★ 改完名旧目录又冒出来：真凶是同步工具自己的 config.xml

**现象**：改名后重启，旧名目录又出现了 —— 但改名其实成功了，新目录里数据完好。
**不是改名失败，是同步工具把它重建了。**

- **机理**：同步工具的文件夹配置里 `path` 一旦还指着旧名，它每次启动都会**按配置把该目录建出来**。
  改名时按纪律关了进程，改完再开，配置没改 → 旧名目录复活（通常只有 `.stfolder` / `.stignore` 两个标记）。
  **凡是"同步根"，改名必须连同步工具的 `config.xml` 一起改，否则等于没改。**
- **★ `config.xml` 的位置各机不同，永远不要猜、不要写死**。
  正解是从 `~\.workbuddy\sync-heal\guard-config.json` 的 `config_xml` 字段反查 ——
  这个字段是装机时写下的本机真实路径，**是全机唯一权威线索**。
  写入时**必须关着同步进程**（它退出时会把内存里的配置覆盖写回，边跑边改必丢）。
- **只改该改的那一个 `path`**：改到目标夹的 `<folder id="..." path="...">`。
  配置里可能还有别的夹带同名 `label` —— 那是**显示名不是路径**，一个字都不许动。
  判据：`label` 是裸词、没有盘符，正则 `/^[A-Za-z]:[\\/]+<夹名>/` 天然匹配不到它 ——
  **这个"改不到"是特性不是 bug**。
- **`<defaults>` 里那条空 folder 节点：是同步工具自带模板，不许动。**
  它不属于 folder 列表，是"新建文件夹时套用的默认值"。删了下次启动会自动生成回来，白折腾。
  判据＝先看它有没有被 `<defaults>` 包裹；报告里只写「`<defaults>` 模板正常」。
- **★ 旧名目录一律先判定再处置，判据分三档**：
  ① **同步壳**（排除 `.stfolder` / `.stignore` / `.stversions` / `~$` 后一个文件都不剩）→ 直接退役；
  ② **重复副本**（文件都在但同名同大小）→ 直接退役；
  ③ **有独有文件** → 先合并（**同名不覆盖**）再退役。
  统计时**必须把同步标记文件排除在外**，否则 `.stfolder` 会被当成"独有文件"合并过去，
  也会让"新目录是空壳"的快路径永远走不到。
- **退役不等于删除**：整体改名到同步夹之外的归档目录留档，用户确认后自己删。
- **★ 前置闸门**：同步配置这一关没过（没找到 `config.xml`，或它仍指旧路径）→ **不许退役旧目录**，
  否则退役完同步工具下次启动又建一个回来，等于白干。脚本里记状态并**硬拦**。

### 19.5 ★★ 逐文件移动会留下「半场历史」：必须配同名复核

实测教训：改名当天关客户端改名、两分钟后重开，
**程序按新路径找正文找不到 → 直接新建了一份同名 `.jsonl`**（同一 sessionId 两份文件）；
之后合并转录目录时发现目标已存在同名文件，为"不覆盖"而跳过 —— 结果那一场会话
**只显示重开之后的内容，之前一上午的全部看不见**（文件还在，只是没人读它）。

- **为什么会漏**：转录文件的路径由 `sessions.cwd` 推出来。
  客户端在「目录还没合并、数据库已改」的窗口里启动过，就会按新路径另建一份。
  **只要改名与重启之间隔着一段时间，这个窗口必然出现。**
- **判定口径（脚本化）**：按数据库 `sessions.cwd` 算出每个会话"应该在哪个目录"，
  同 sessionId 出现在别的目录的文件一律视为碎片。
- **修法**：碎片按首条时间排序（去掉开头的元数据行）拼到正式件**前面**，
  两份原件整字节备份，碎片原样留原地不删；复读行数与首末时间核对。
- **★★ 归并必须幂等**：碎片内容已进正式件后，**必须把碎片改名或移出转录区**。
  否则下次谁再跑一次归并脚本，**同一段正文会被再并一遍、字数翻倍** ——
  而"再跑一次看看"恰恰是人最自然的动作。检测口径也随之干净：只认 `.jsonl` 结尾的文件。
- **验收判据不能只看"文件存在"**：`99/99 转录到位` 也可能其中一条只有后半段。
  要额外查一次**同 sessionId 是否跨目录重复**。这是 19.1 判据的补丁。

### 19.6 不该改的别改

专家名、文档刊头署名、技能触发词、历史报告与审计日志里记载的旧路径文字 ——
**都是当时的事实记录，改了＝篡改历史**。
残留引用按「是不是功能指针」分两类：功能指针（19.2 表的 4 / 5 / 6）必改；纯文本命中一律不动。

### 19.7 ★★ 第二台机器必须拿到「与第一台同版的完整作业包」

实测教训：作业包在两机之间靠聊天软件发，**中途迭代了三次**，
第二台手上是**第一版**。结果第一台跑完六步、第二台只做了"改名 + 改数据库"两步，
同步工具的 `config.xml`、数据库的 `workspaces` 行、转录目录全留了尾巴 ——
现象就是「**文件夹已经叫新名了，但工作区列表里没有它**」。

- **纪律**：任何多机作业，**每次包一改，就要把"第二台机器需重新取包"当成一次交付动作**，
  不能只在手册里写一句"记得重传"。
- **版本对账手法**：包内每个脚本的**字节数与修改时间**写进手册；
  对端窗口首行打印包版本，跑完把报告发回。**靠人对比"是不是同一版"必然出错。**
- **更好的形态**：把收尾 / 体检脚本放进**同步范围**（工作区），文件层自动推到对端，
  就不存在"版本不一致"这个变量。只有**改自己脚下地板**的那类脚本（如改名脚本）
  才必须放在同步范围外。

### 19.8 收尾要「一个入口」，不要「七个 bat」

用户原话反馈：「你写的很复杂，我看不懂每一步要怎么做」。

- 第一版给了六个入口 —— **对非技术用户等于没有入口**：他不知道该双击哪个、什么时候双击。
- 第二版收敛成**一个脚本、一个 bat**，内部按序做完七件事
  （现场 → 转录目录 → 数据库 → 守卫配置 → 显示名 → 同步配置 → 验收），
  **最后把现场事实写成一份 txt 报告**（比打印在窗口里更可靠，能回传对账）。
- 纪律：**能自动判断的绝不问用户，能一个入口做完的绝不给两个**；
  前置条件（关客户端 / 关同步）由脚本自己检测并等待，不要求用户记顺序。
- 报告要写得「能对账」：每项给 **OK / 待做 / ! / X** 四态结论 + 具体路径 + 条数，
  用户只需把 txt 发回，不必口述窗口里看到了什么。

### 19.9 ★ 两台的同步夹清单可能本来就不一致：收尾要并排对一遍

改名收尾最容易只盯「工作区那一条」，漏掉**两台机器的 folder 清单本身就不同**这件事。

- **实例**：A 机 `config.xml` 有 5 条 folder，B 机只有 4 条 —— 少的那条是
  **后加的同步夹**（A 机某天才建，B 机装机时还不存在）。
  **后加的同步夹不会自己跑到另一台机器上**：folder 配置是**本机本地配置**，不随同步内容走。
- **收尾必做**：把两台的 folder 清单（`id` + `path` + `type`）**并排列出来对一遍**，
  差异逐条给去向，不要"我这台跑完就完了"。
- **★ 看门狗是同一个坑，而且是写死的**：守卫脚本的文件夹清单如果写死，
  **不在清单里的同步夹 = 完全不受看护**（加密口令污染、设备条目缺失、暂停状态都不查）。
  加同步夹时必须**连带决定"这台机器要不要也纳入看护"**。
  **改清单前先核对该夹的 device / type 现状**，别让看门狗第一次跑到它就动手改配置。
- **判"数据对不对得上"时，计数口径要先对齐**：两台对同一目录曾数出**相差近 2000 个文件**，
  看着像缺件，实际是其中一台的脚本把 `build` / `node_modules` / `__pycache__` 等排除在外。
  换成同一口径后只差几十个＝当天新产出的未同步文件。
  **先对齐口径，再下"是否有缺口"的结论。**

### 19.10 ★★ 冲突副本 `*.sync-conflict-*`：清可以，但**只搬不删、先验正本**

**来源**：两台机器同时写同一个文件。实测三类高发区 ——
专家包运行副本（两边同时改 / 本机标记撞名）、技能目录里的**本机迁移标记**、
市场清单 `marketplace.json`（两边装插件时各写一次）。
**它们不会自己消失，只会越积越多。**

**命名与正本推导**（清之前必须先做这一步）：
`<原名>.<扩展名>` → `<原名>.sync-conflict-<yyyymmdd>-<hhmmss>-<设备短ID>.<扩展名>`
（名字里的设备短 ID 就是"谁写出来的"）。去掉 `.sync-conflict-…-<设备ID>` 这一段，
剩下的就是**正本名**。

**★ 硬闸门：正本不在的副本一律不动** —— 可能是唯一副本，清了就是事故。

**纪律**：

1. **只搬不删**：搬到**同步夹之外**的归档区（脚本里加断言：归档路径不得落在任何同步夹内），
   保留原目录结构，另出 `manifest.txt` 记 **原路径 / 副本大小与时间 / 正本大小 / 归档去向**。
2. **副本比正本大的要单独标 ★** —— 说明内容有分叉、不是纯重复，将来追溯先看这几份。
3. 搬完**触发重扫**（`POST /rest/db/scan?folder=<id>`），删除会同步到对面，**两台一起干净**；
   对面自己的同名冲突副本（名字里带**它**的设备 ID）也会随这次删除消失。
4. 归档区不参与同步，可长期留档。

**实测一次**：五个夹共 26 个冲突副本，0.35 MB，其中 9 个比正本大；清完同步夹内归零。

## 二十、★★「自建专家召唤不了」的头号成因：会话选了专家（定版）

> **这一章是"文件到了、专家却不生效"里最反直觉、也最容易白查一天的一类。**
> 它跟登记层、跟包、跟配置**全都无关** —— 先把这条排掉，再去查别的地方。

### 20.1 病症与代价

会话里召唤自建专家报 `Task agent <name> is not available`，`Duration` 只有 1~5ms。
**重启客户端、重装专家包、改 `settings.json`、改 `installed_plugins.json`、改 `marketplace.json`、
重建 cache 副本、查 `workbuddy.db` —— 全部无效**，因为问题根本不在这些地方。

**一句话结论（分两支，别只记第一支）：**

- **会话选了专家** → 平台把**该专家的插件置 `true`、其余全部自建专家插件置 `false`**；
  插件没启用 → 不进 active 列表 → AgentManager 里不注册 → 召唤必然失败。
- **会话没选专家** → **全部自建专家插件都是 `true`**，此时**同一条会话里可以同时召唤任意多个专家**
  （20.5 实测三路并行全部成功）。
  **"只能一个专家在场"是选了专家之后才成立的，不是全局限制。**

### 20.2 判据（一条命令定性，别再做别的排查）

看当天工作区日志里设置加载器那几行：

- 该行**同时**出现 `"conversationTags":{"expert":"<某专家>"}`，且 `"enabledPlugins"` 中
  自建专家市场系列**只有该专家为 `true`、其余为 `false`** → **确诊**。
- 同一行**没有** `conversationTags.expert`，自建专家全为 `true` → 这条会话没选专家，正常。

辅助判据：失败时的 `available=[…]` 列表里，自建专家**只剩会话选中的那一个**。

### 20.3 三个必须记住的事实（反直觉，全实测）

1. **磁盘上的 `settings.json` 与故障无关。** 故障期间它一直是全 `true`；
   会话级的 false 是**运行态覆盖**，不落盘。所以"打开设置文件看开关"永远看不出问题。
2. **重启客户端没用**（这是最坑的一点）。插件表在**会话宿主进程启动时固化**：
   只在进程初始化时读一次 `enabledPlugins`，之后用的是**内存快照**，不跟文件走。
   重启后重开的仍是**同一条带 expert 绑定的会话** → 照旧只启用一个专家。
   （实测：某进程 17:39 起、期间文件已被改成全 `true`，它到 18:05 仍报 `active=15`。）
3. **沙箱重启也不刷新插件表。** 日志里沙箱重启成功只重启了 CLI 子进程，
   插件表在会话宿主（工具进程）里，两者不是一层。

### 20.4 修法（二选一，都只动界面）

| 方案 | 动作 | 适用 |
|---|---|---|
| **A（首选）** | **新开一条对话，不选任何专家**，在那边召唤 | 零风险、必成。实测新建的不选专家会话，10 个自建专家插件全部 `true` |
| B | 在当前会话**取消专家选择 → 重开这条会话** | 需要在同一会话里继续时用；重开是为了让宿主进程重建插件表 |

> **互斥只在"选了专家"的会话里成立**：会话里已选中某专家时，
> 「保留该专家在场」与「召唤其他专家」不能兼得，这是平台机制不是 bug。
> **但只要这条会话没选专家，就不存在这个限制 —— 可以在同一条会话里并行召唤多个专家**（见 20.5）。
> 需要**专家身份常驻**（专家以自己的角色与知识库持续在场）时才走**专家团**路线。

### 20.5 同会话并行召唤多个专家：实测通过

在一条**未绑定专家**的会话里并行派发三个自建专家子任务，结果三个全部完成回执。

判定要点（**三条独立证据同时成立**才算通过）：

1. 日志出现 `[MCP][registerAgent] agent=<name>` —— 说明该专家已进 AgentManager（失败时这里没有它）；
2. 紧邻出现 `AgentManager.rebuildAgents: completed` —— 注册流程走完；
3. 回执里**列出真实的知识库文件名** —— 空跑或占位回复不算通过。

补充实测：真专家**首次响应偏慢**（要读几十份知识库），2~3 分钟属正常，
**不要因为"迟迟不回"就判定失败**。回执里也能看出插件实际加载的版本。

### 20.6 排查顺序（照这个走，别乱撞）

1. `grep "conversationTags"` 当天工作区日志的设置加载行 → **先看有没有选专家**。
2. 有 → 20.4 修法，结束。**不要再查包、查清单、查 cache、查 db。**
3. 没有 → 才回到常规链路：第四节排错表「文件到了，专家不出现」→ 五层登记 → 自愈脚本。

### 20.7 顺手记下的两处非主因（不要误当主因）

- 自建专家市场的 `marketplace.json` 可能**少登记**若干专家包，个别包还会被登记进自动生成的
  市场条目。**它影响的是跨机"五层登记"的一致性，不会导致本机召唤失败** —— 本次即被误判过。
  实测印证：某个"未登记"的包在本机日志里**正常注册**（`[MCP][registerAgent] agent=<name>`），
  **再次证明市场登记缺失不影响本机召唤**。
- `workbuddy.db` 的 `sessions` 表虽存会话与插件上下文字段，
  但**没有**任何"会话级插件开关"字段；相关字段实测为空。

## 二十一、★★ 某个夹永久「未同步」：删目录被忽略文件挡住（定版）

### 21.1 病症：界面说「未同步」，但病根不是"连不上"，是"删不掉"

**你看到的**：

- 同步面板里**某一个夹永久显示「未同步」**，其余夹「最新」；
- 「远程设备」那一栏显示 `同步中 (95%, 0 B/s)`；
- 「此设备」上下行**都是 0 B/s**，运行时间正常、监听正常、设备发现正常。

**最容易误判的三个方向，本次全查过，全是好的**：断连 / 设备登记缺项 / 加密口令。
**真正的指纹只在日志里**：

```text
WRN Failed to sync (path=<夹内路径> error="syncing: delete dir: directory has been
    deleted on a remote device but contains ignored files
    (see ignore documentation for (?d) prefix)" folder.id=<夹 id>)
INF Failed to delete directory (dir.name=<夹内路径> error="directory ...")
INF Folder failed to sync, will be retried (wait=1m0s → 2m0s → 4m0s → 8m0s ...)
```

**关键区分口径**：`/rest/db/status` 的 **`state=idle` 但 `errors` / `pullErrors` 非 0**。
`state=idle` 会骗人（看着"闲着没事"），**`errors` 才是真相**。

### 21.2 机理：这是第十八节那套忽略规则的**副作用**

链条：对端卸载 / 删除了某个目录 → 同步过来要求本机跟着删 →
但该目录里还留着 `.in_use` / `.orphaned_at` 这类**已被 `.stignore` 忽略**的本机标记 →
同步工具默认**拒绝删除"内含忽略文件"的目录**（怕误删"不归它管"的东西）→
该夹进入 `Folder failed to sync` → 指数退避重试 → **永久卡住，且不上报界面**。

> **第十八节治好了"本机标记跨机撞名产生冲突副本"，却换来了"目录删不掉"。两件事必须一起治。**
> 判据：**缺 `(?d)` = 这个坑**；`(?d)` 齐了还删不掉 = 才去看是不是文件正被进程占用。

### 21.3 修法：`(?d)` 前缀 + **就地升级**（绝不能追加）

`(?d)` 是同步工具的官方修饰符：**父目录被删时，允许一并删掉这个被忽略项**。
只影响"父目录本身都没了"这一种情形，**不会让同步工具主动删任何东西**，对正常文件零影响。

**★ 致命细节：同一条 pattern 的裸形式与 `(?d)` 形式不能并存。**
忽略匹配是**逐条按顺序**判定的、任一条命中即生效 —— 裸行排在前面，`(?d)` 永远轮不到，
**看着配了、实际照旧卡死**。

所以 `同步忽略登记.py` 里三处必须同时改：

| 位置 | 改什么 |
|---|---|
| `RULES[...]["required"]` | 每一条都带 `(?d)` |
| 新增 `_normalize_d(lines, required)` | 把裸行**就地升级**、并去掉同模式重复行；纯函数、可单测 |
| `audit()` | **先 `_normalize_d` 再判 missing**；且"只有升级、没有缺项"时也要写回 |

**★★ 血的教训：光改 `.stignore`、不改程序，45 秒就被打回。**

现场：先手工把 `.stignore` 改成 `(?d)` 形式（API 复读一致、看着成功了），
**45 秒后自愈程序按旧 `RULES` 把裸行又追加回来**，变成"`(?d)` 行在前 + 裸行在后"的
**更糟状态** —— 不但没修好，还多出 3 行冗余。

> **`RULES`（分发源）才是权威；手工改 `.stignore` 只能应急。**
> 正解见第十二节：改**分发源**的同一份脚本 → 再 `copy2` 到运行副本（或等自更新取走）。
> 实测：改完分发源后，**运行副本在手工 copy 之前就已被守护自动取走**（哈希已一致），
> 对端也在 45 秒内取走并按新规则补齐自己的 `.stignore`。

### 21.4 现场数据（修前 → 修后）

| 项 | 修前 | 修后 |
|---|---|---|
| 卡住的那个夹 | `state=idle` 但 **errors=2 pullErrors=2** | **errors=0 pullErrors=0** |
| 对端完成度 | **永久 95%**（needBytes=0，上下行 0 B/s） | **100.00%** |
| 死循环 | `Folder failed to sync` **157 次**、`contains ignored files` **603 次**、退避到 `wait=8m0s` | 最后一次失败定格在那一刻，此后 **0 新增** |
| 卡住的目录 | 那一个专家包目录（只剩被忽略的本机标记） | 已删除（日志 `INF Deleted directory`） |
| 顺带 | — | 同一秒连删 **7 个积压旧版本目录** |
| 五个夹 | 1 个未同步 | **全部 100%** |

起因：对端**卸载了某个专家包**（本机源包夹与该市场清单里均已无它 —— 见 20.7 曾提过这个包"没登记"，
本轮它是**被正常下架**）。清单里可能仍留一条孤儿登记（自愈按约定"只报告不摘除"，不影响同步与召唤）。

> **查源包时的路径坑**：源包不在 `marketplaces\<市场名>\<专家名>`，
> 而是在 `marketplaces\<市场名>\plugins\<专家名>`。
> 按前者查会把**全部专家**误判成"孤儿登记"（本轮即误报过 15 个，实为路径错）。

### 21.5 排查顺序（别再从"网络 / 口令 / 设备登记"查起）

1. `GET /rest/db/status?folder=<卡住的夹>` → 看 **`errors` / `pullErrors`**（本题指纹：非 0 且 `state=idle`）
2. 读**真日志**搜 `contains ignored files` / `Folder failed to sync`
3. `GET /rest/db/ignores?folder=<id>` → 看规则里**有没有裸形式**（不以 `(?d)` 开头）
4. 改**分发源**的 `同步忽略登记.py` → `copy2` 到 `~\.workbuddy\sync-heal\` → 跑一次
5. 验收：该夹 `errors=0` **且** `completion=100%`，日志出现 `INF Deleted directory`

### 21.6 一句话记忆

> **界面说「未同步」，先看 `errors` 而不是 `connecting`；
> 删不掉的目录，十有八九是被自己的 `.stignore` 挡住了 —— 给它加 `(?d)`。**
